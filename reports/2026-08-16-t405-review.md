## [MEDIUM] R405-1 PRのbase/head更新時にT404 revision mappingが実行されず、同一PRコンテキストを継続できない

### Failure mode

`src/t405-review-contexts-runtime.ts` の `redetectPullRequest` は、既存PRコンテキストを見つけた場合、保存済みbase/headと再検出したbase/headが完全一致するときだけ `contextStateService.update` を呼ぶ。SHAが変わっている場合は更新せずそのままreturnする。

一方、T404の `GitHubPullRequestContextStateService.update` はbase/head変更をrevision変更として扱い、`mapRevision` を必須で実行してからatomic commitする契約になっている。しかしT405 runtimeが生成するstate serviceには、revision mapperとして常に `Revision remapping is not a layer-toggle operation` をthrowする関数が渡されている。

そのため、例えばPRへcommitが追加されてHEADがBからCへ進んだ後に再検出すると、View上のin-memory current PRだけCへ変わり、永続Review StateはBのまま残る。その状態でlayerを切り替えるとT404 updateがB→Cのrevision変更を検出してmapperを呼び、必ず例外になる。再起動後も保存済みPRはBへ戻る。

### Requirement / impact

設計6.1はbase/headをcontext identityではなくcurrent revisionとして保持し、PRへcommitが追加されても同じコンテキストを継続すると定義している。T405はT404に依存しているため、このrevision継続経路をproduction compositionへ接続する必要がある。

現在の実装では通常のPR更新で保存状態・layer操作・再起動復元が不整合になる。

### Required direction

T405のPR再検出経路からT404の実revision mapperを利用し、base/head変更時に既存context/global stateを新revisionへmappingしてcommitすること。SHA変更を含むruntimeテストを追加し、再検出後の永続state、layer切替、restart復元まで確認すること。

## [MEDIUM] R405-2 GitHub上でopen PRがclosed/mergedになっても永続PR stateを更新せず、AC-21のclosed PR管理へ遷移できない

### Failure mode

T405のPR再検出はT401 `findOpenByHead` だけを使用する。このadapterはGitHub `/pulls` を `state=open` で検索し、T405の `pullRequestState` もstateを常に `open` として生成する。

保存済みopen PRがGitHub上でcloseまたはmergeされた後に再検出すると、open検索は候補0件となる。T405は `source.setCurrentPullRequest(..., undefined)` を行うだけでreturnし、T404へclosed/merged stateを保存しない。永続コンテキストは引き続きopenのままで、Review Contextsではsaved-openとして表示され、open既定のlayer状態も残る。

`test/unit/review-contexts-storage.test.ts` のclosed PRテストは最初から `state: "closed"` のfixtureを保存して列挙できることだけを確認しており、この実運用遷移を証明していない。

### Requirement / impact

T405の終了条件はAC-21 `closed PR並列管理` であり、設計14/16.4ではclosed PRをcontextとして保存し、既定layerを無効にしてopen PRと並列管理することが要求される。T406はこのシナリオの統合試験を追加する後続タスクだが、production遷移そのものはT405に必要である。

現状ではT404が持つopen/closed/merged保存能力がproduction UIから到達できず、実際に閉じたPRをclosed PRとして管理できない。

### Required direction

既存PR identityについてGitHubの現在stateを取得できるproduction経路を追加し、open→closed/mergedをT404 stateへ永続反映すること。close/merge後の再検出でsaved-closed/mergedへ移り、既定layerがOFFになることをruntimeテストで確認すること。

## [MEDIUM] R405-3 Review Contextsから開くdiffがT302のcanonical review diff経路を迂回し、diff上の確認・解除操作が失敗する

### Failure mode

`src/t405-review-contexts-runtime.ts` は独自の `review-range-pr-context` schemeとin-memory `ReviewContextDiffDocumentProvider` を新設し、ランダムtoken付きURIを作って直接 `vscode.diff` を開く。

既存T302/T303経路は `ReviewDiffEditorController` / `ReviewDiffUriCodec` により `review-range-diff` canonical URIへcontext ID、filesystem semantics、side、revision source、immutable revision、file pathを埋め込み、既存content providerとreview commandへ接続している。

`src/extension.ts` のdiff review command経路は、対象document schemeが `review-range-diff` でなければ `Review Range diff editor is not available.` をthrowする。そのためReview Contextsから開いた `review-range-pr-context` diffでは、確認済み/解除操作を実行できない。また独自URIはcanonical context/revision identityを保持しない。

### Requirement / impact

T405はT302に依存し、設計8章は仮想diff文書のcanonical identityを規定している。Review Contextsの「diffを開く」は既存レビュー機能へ接続される必要がある。

現在はdiff自体は表示できてもレビュー操作不能な別系統のdiffになり、T302/T303との統合契約を破っている。

### Required direction

独自 `review-range-pr-context` providerを使わず、T302の `ReviewDiffEditorController` / canonical content providerへT405のcontext/base/head/fileを渡してdiffを開くこと。Review Contextsから開いたdiffでoriginal/modified双方の確認・解除が動くruntime/Extension Hostテストを追加すること。

## [MEDIUM] R405-4 「コンテキスト表示から削除」がcurrent contextではno-opになり、後から非current化した時だけ突然非表示になる

### Failure mode

`ReviewContextsController.hide` は指定context IDをvisibility storeへ保存するが、`projectReviewContexts` は `hiddenContextIds` をsaved contextにしか適用しない。current contextはhidden IDに入っていても必ず表示される。

一方、`package.json` の `reviewRange.hideReviewContext` menuはReview Contextsの全itemへ表示される。そのためcurrent PR/branch/workspaceで「表示を削除」を実行すると、操作は成功扱いでhidden IDが永続化されるにもかかわらず直後のViewから消えない。後でそのcontextがsaved扱いへ変わると、以前のhidden IDが効いて初めて消える。

`test/unit/review-contexts-ui.test.ts` もcurrent PRをhidden setへ入れたまま表示されることを期待値として固定している。

### Requirement / impact

設計16.4は「各contextの操作」に「コンテキスト表示から削除」を含め、T405終了条件も履歴を消さず表示だけ削除できることを要求する。

現在はUI上提供される操作と実結果が一致せず、遅延して別タイミングで非表示になる副作用もある。

### Required direction

要求どおりcurrent contextもpresentation-onlyに非表示化できるようprojectionを修正すること。もしcurrentを非表示不可とする仕様へ変更するなら、少なくともcommand/menuをcurrent itemから提供せず設計・タスク定義も合わせる必要がある。現行仕様を前提にcurrent PR/branch/workspaceのhideテストを追加すること。

## [MEDIUM] R405-5 Review Contexts Viewに設計で要求された各contextの進捗表示がない

### Failure mode

設計16.4はReview Contexts Viewの「各contextの操作/表示」として `進捗表示` を要求しているが、T405の `ReviewContextListItem` にはprogress情報が存在せず、`ReviewContextsTreeProvider` が表示するのはcurrent表示、PR title/state、layer状態、base/headだけである。

T405 runtimeからT304のPR progress計算/Tree境界へ接続する処理もなく、追加テストにも進捗表示の検証がない。

### Requirement / impact

T405はT304を直接依存に持ち、Review Contexts Viewで現在PR・保存済みPRを並列管理する際の進捗表示は設計上の機能である。

現状はcontext一覧と操作の一部だけが実装され、View仕様が未完了である。

### Required direction

T304の既存progress契約を再利用して各PR contextの進捗をprojectionし、Review Contexts rowへ表示すること。非PR contextについて設計上必要なprogress表現も既存Review Stateから一貫して算出し、少なくとも現在PR・saved open/closed PRの表示テストを追加すること。

## [LOW] R405-6 `reviewRange.closedPullRequestLayerDefault` 設定が公開されているがruntimeが参照せず、値を変更しても挙動が変わらない

### Failure mode

`package.json` は `reviewRange.closedPullRequestLayerDefault` をboolean設定として公開している。しかしT405のlayer表示/既定値は `isPullRequestDecorationEnabled` の `decorationEnabled ?? state === "open"` だけで決まり、設定値を読むproduction codeがない。

`test/unit/review-contexts-runtime-wiring.test.ts` も設定項目のdefaultがfalseであることしか確認していない。

そのためユーザーが設定をtrueへ変更してもclosed PRの既定layerは常にOFFのままで、公開設定が無効である。

### Required direction

この設定を提供するならclosed PR contextのdefault layer決定へ実際に配線し、false/true双方をテストすること。設計どおり固定OFFで十分なら、効かない設定項目自体を削除してUI上の誤解をなくすこと。
