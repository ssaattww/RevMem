## 指摘事項

- 指摘要約: High 2件、Medium 4件、Low 2件
  - **High-1・blocking validation / fallback** — `src/core/pr-progress/pr-diff-progress.ts:219-230`はstatus matrixとpath重複を確認した後、`decision.excluded`なら`changedCoordinates`を呼ばずreturnする。したがってuser/default globで除外された非binary fileでは、unknown `DiffLine.kind`、context-only hunk、座標不一致、hunk order/delta不一致、source統計不一致をすべて受理する。入力snapshotの妥当性がexclusion policyに依存し、同じcacheが設定変更前は成功・設定変更後はfailureとなる。T402の「欠落・不完全patchを検出し、全経路失敗時に推測しない」に対しても、現在除外中のfileだけ不完全patchを見逃す。binary以外は除外判定にかかわらず構造validationを先に完了し、集計だけを除外する必要がある
  - **High-2・blocking contract / follow-on path integrity** — `:166-189`のstatus matrixは一方の表示pathしかpolicyへ渡さないため、`modified`・`renamed`・`copied`の非表示側pathをrepository-relative pathとして検証しない。例として`oldPath="../outside.ts"`, `newPath="src/a.ts"`は通り、raw oldPathがfile progressへ返る。さらに`modified`のold/new path不一致、`renamed`/`copied`の同一path、`added` hunkにold-side context、`deleted` hunkにnew-side contextを許し、status分類と実diff sideが矛盾したsnapshotを受理する。T304分類とT302/T303のoriginal-side content解決へ不正path・誤分類を渡さないため、両pathをcanonicalizeし、statusごとのpath equality/inequalityとhunk side invariantを検証する必要がある
  - **Medium-1・blocking state consistency** — `:230-238`は`state.lineCount`をmodified reviewed intervalの上限にだけ使い、同じhead revisionのactual addition座標が`lineCount`以内かを検証しない。`lineCount=1`、addition coordinate 100、modifiedReviewed空ならerrorにならず0/1を返す。review済みintervalが存在するときだけ破損を検出するため、同一revisionのdiff/state整合がreview操作の有無で変わる。stateが存在する場合は全modified-side hunk coordinateまたは少なくともaddition最大値がlineCount以内であることを確認する必要がある
  - **Medium-2・blocking TDD / acceptance coverage** — current testは全確認4/4とzero denominatorだけで、non-zero file単位の`reviewedLineCount`・`totalLineCount`・部分率、PRの部分集計をassertしない。除外testもaggregate numerator/denominator/progressと`excluded`をassertしないため、除外fileが分母へ混入しても検出できない。またmalformed excluded file、secondary path traversal、modified/renamed path matrix、diff coordinateとlineCount不一致、explicit hunk gap mismatchが未testである。T301のPR/file calculator終了条件とT402/T304向けcontractを失敗testで固定する必要がある
  - **Medium-3・blocking standards regression** — `src/core/pr-progress/pr-diff-progress.ts:6-40`ではR3で追加された公開DTO propertyのJSDocが再度失われ、公開functionのsummaryだけが残る。`PullRequestDiffSnapshot`のidentity、pathのraw/normalized区別、除外時count、zero denominator、file順序が型定義から読み取れず、PR本文の「公開DTOへ規約を文書化」と一致しない。公開interface property documentationを復元する必要がある
  - **Medium-4・blocking evidence** — current PR本文はR3までのTDD証跡と「最終HEAD runは後で記録する」という記述のままで、R4/R5のtest-first、implementation、diagnostic fix、current head/runを反映していない。implementation reportはR5まで更新済みだが、PR説明とsource/testの再現証跡が一致していない。PR本文へR4/R5 dispositionとcurrent head `4b0f806...` / run `30147550473`を同期する必要がある
  - **Low-1・held performance/robustness** — `:63-75`はreviewed intervalを1行ずつSetへ展開する。original側にはupper boundがなく、modified側もsafe integerなら巨大`lineCount`を許すため、破損stateの巨大intervalでExtension Hostを同期的に長時間占有できる。changed座標をinterval検索する方式または明示上限が望ましい
  - **Low-2・held numeric/identity boundary** — context ID、base/head SHA、file IDの空文字、base=headを許し、file合計・aggregate合計・hunk anchor/delta演算後のsafe integerを再検証しない。通常規模では発生しにくいが、pure API boundaryとして空identityとderived overflowをrejectする余地がある
- R5 finding disposition:
  - R5 High-1 unknown line kind/status: included fileではexhaustive runtime validationへ変更されclose可能。ただしHigh-1のとおりexcluded nonbinary fileではline validation自体をskipする
  - R5 High-2 context-only hunk: included fileではchanged line必須となりclose可能。ただしexcluded nonbinary fileではskipする
  - R5 Medium status matrix: unknown/missing pathと一部count matrixは改善したが、両path canonicalization、path equality、added/deleted hunk side invariantsが残るためpartial close
  - R5 Medium canonical path duplicate: display/current pathのduplicateはrejectするためclose可能
  - R5 Medium lineCount: reviewed interval上限は改善したがactual diff座標との整合が残るためpartial close
  - R5 Medium cumulative test: contextId/originalDiffId/opposite-side/context coordinate/duplicate actualは復元された。partial/file progress、excluded aggregate、explicit gap、今回の新規境界は未固定
- 追加確認でfindingなし: included fileのunknown runtime union拒否、included hunkのchanged-line必須、canonical display path重複拒否、state payload ID/revision拒否、modified interval上限、addition/deletion side別intersection、zero-count anchorとcumulative delta、head SHA限定current-main merge-ref CIには上記以外の問題を確認しなかった

## 結果

- 結果: **Fail・Request Changes相当**。R5の主要修正は前進したが、除外時にdiff validationをskipするHigh 1件とstatus/path/hunk contractのHigh 1件、state整合・TDD・documentation・evidenceのMedium 4件が残る
- head `4b0f8067088e4b48cf5176efe48291c418ab8099`のCI run `30147550473`は全工程success。ただしcurrent testがpolicy-dependent validation、secondary path、partial/file進捗、diff/state lineCount整合を検出しないためCI successはfindingsを否定しない
- branch headはcurrent mainにbehind 1だが、CI対象merge ref `bb69afb195d295aa665f50f43892e29fd206e039`はcurrent mainを含む。このbehind状態単独はblocking findingにしない
- 修正はmalformed excluded file、status/path/hunk matrix、actual coordinate/lineCount、partial file/PR進捗、excluded aggregateをtest-firstで追加し、その後にvalidation順序・path normalization・state整合・公開文書・PR証跡を修正する必要がある

## リスク

- user exclusionの有無で同じdiff snapshotのvalid/invalid判定が変わり、設定再評価やT402 fallbackで不完全patchを見逃す
- raw oldPathや誤statusを後続diff provider/Tree Viewへ渡し、repository外pathまたは誤分類を扱う可能性がある
- same-revision stateのlineCountとactual diffが矛盾しても未確認状態では検出されず、破損cacheを正常な0%進捗として表示する
- file単位・部分進捗と除外aggregateの回帰がtestで固定されていない
- 巨大intervalとderived integer overflowはnon-normal pathのheld riskとして残る
