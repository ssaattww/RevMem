## 指摘事項

- **高・blocking normal-path** — `applyGitFileStateTransitions`はcloneしたactive stateをsectionごとに即時変更し、その後のrename/delete元を更新済み`currentPath`から再検索する。このため、同一diff内の正常な同時transition `a.ts -> b.ts` と `b.ts -> c.ts`、swap `a.ts -> b.ts` と `b.ts -> a.ts`、既存`b.ts`のdeleteと`a.ts -> b.ts`の組合せがdiff section順に依存する。全source file IDを変更前snapshotから先に解決し、rename・deleteを含む全transitionの一意性とdestination衝突を検証してから一括適用する必要がある。現testは独立したdirectory moveのみで、chain、swap、delete+rename衝突を検出しない

- **高・blocking conservative-state** — 曖昧なrename、duplicate candidate、missing sourceでは`unresolved`へ記録するだけで、入力`files`からcloneした旧source stateを`modifiedReviewed`付きのまま返す。設計3.1、9.1、9.7、AC-10、AC-24は曖昧・追跡不能な範囲を未確認にすることを要求するが、返却snapshotには`InternalReviewState.unresolved`を表現するfieldがなく、旧path・旧revision・旧確認済みintervalが残る。callerが`unresolved`を無視または適用漏れすると確実に誤表示するcontractであり、API自身がsource/destinationを未確認化するか、適用必須のdeterministic transition commandを返す必要がある

- **高・blocking requirement gap** — 設計9.4はcopyを「新規ファイルとして未確認から開始」、T204終了条件はcopy・分割・統合・複数候補を「新規未確認」にすると定義する。しかし現実装はcopy sectionについて`unresolved`を返すだけでdestination `FileReviewState`を生成せず、plain additionも`other`として無視する。結果の`files`にはcopy先・分割先・統合先が存在せず、入力にもdestination file ID、line count、state factoryがない。現test名はsplit・mergeまで扱うと主張するがfixtureは2件のcopyだけで、destinationが未確認stateとして生成されたことを検証していない

- **高・blocking state-integrity** — 内容変更を伴うrenameでも`active[fileId] = { ...current, ... }`により旧`contentHash`をそのまま保持する。`FileReviewState.contentHash`は現在内容の確実性確認用であり、revision・path・lineCountだけ新しくして旧hashを残すと、T105/T205/T502などの後続certainty checkが新revisionの内容を旧hashで検証する不整合stateになる。新内容hashを入力できない現APIでは、hunkがあるrename時は少なくとも`contentHash`を除去し、100% renameのみ保持する必要がある。現test fixtureは`contentHash`を設定していないため検出できない

- **高・blocking settings contract** — T204は`options`を受け取るが、T203 mapperへ`oldText`と`newText`を渡していない。T203実装はEOL-only判定とwhitespace-only判定の安全性証明に全文textを必須とし、textがなければ`ignoreEolChanges`も`ignoreWhitespaceChanges`も変更hunkを無視しない。したがってrenameと同時に空白だけ、CRLF/LFだけ、末尾改行だけが変わった場合、ユーザー設定がtrueでも確認済み範囲が解除される。設計9.6とT203/T204接続contractを満たすにはold/new textをT204入力へ追加してmapperへ渡すか、設定を受け取らない明示的contractへ変更する必要がある

- **中・blocking standards gate** — 新規公開APIである`GitFileTransitionUnresolvedReason`、`GitFileTransitionUnresolved`、`GitFileStateTransitionInput`、`GitFileStateTransitionResult`、各property、`applyGitFileStateTransitions`にJSDocがない。特に`files`が完全snapshotなのかtransition対象だけなのか、unaffected fileのrevisionを更新するのか、`unresolved`時の旧stateを誰が無効化するのか、新規file IDを誰が生成するのか、例外時にpartial resultが存在しないことが定義されていない

- **中・blocking performance** — rename 1件ごとに`mapReviewedIntervalsAcrossDiff`が完全diffを再parseし、さらに直後の`parseZeroContextGitDiff(input.diff)`でも完全diffを再parseしている。N件のdirectory moveでは同じdiffを約`2N+1`回解析するため、diff sizeもNに比例する通常ケースで概ね二次時間になる。設計20章は差分適用をfile単位とし、大規模PRでExtension Hostを長時間占有しないことを要求する。parser結果を1回だけ生成し、file section単位mapperへ渡す構造が必要

- **中・state validation** — `lineCount`は旧stateへhunk deltaを加算するだけで、旧`lineCount`、delta、加算結果が非負safe integerであることを検証しない。破損snapshotまたは不整合diff/stateの組合せで負数・unsafe integerを返却でき、`modifiedReviewed`が新lineCount外へ残っても検査しない。確実性優先なら不整合時はthrowまたは対象file未確認化が必要

- **中・conservative-failure** — copy metadata専用`decodeQuotedPath`は最初の閉じquoteでreturnし、閉じquote後の余剰文字を検証しない。`copy from "src/a.ts"junk`を`src/a.ts`として受理する。また同一section内のduplicate `copy from`/`copy to`は後勝ちで上書きされ、copy metadataとdelete/rename metadataの矛盾も拒否しない。T203 parserのmalformed input拒否方針と不整合である。共通decoder・metadata state machineを再利用し、duplicate/conflicting metadataを拒否する必要がある

- **中・revision contract gap** — 返却`files`は完全snapshotに見える一方、rename/delete以外の`other` fileとdiffに現れないfileは旧`revisionId`・旧`updatedAt`のまま残る。同一`ReviewContextState.files`内で新revisionへmapped済みfileと旧revision fileが混在すること自体は許容可能だが、公開contractにその意味がなく、T205がcontext revisionを進める際にどのfileを追加mappingすべきか決定できない。完全snapshotを返すならfile単位revision混在を明文化し、normal modified fileはT203の別経路で必ず処理されるcomposition testが必要

- **中・process/evidence gap** — PR差分にT204実装レポートと`tasks/tasks-status.md`更新がなく、task表はT204を依然「次」、現在タスクなし、branch/PRも旧T300のまま示している。PR本文はTDDを主張するが、Red commit/run、Green commit/run、実行test数、scope、既知riskをrepository内証跡として追跡できない

## 結果

- 結果: **fail・follow-up必須**
- blocking finding: 7件
  - transition逐次適用によるstable ID破壊
  - unresolved時に旧確認済みstateを保持する保守性違反
  - copy・split・merge・addition先を新規未確認stateにできないrequirement gap
  - 内容変更rename後のstale `contentHash`
  - whitespace/EOL設定がT204経由で機能しないcontract断絶
  - 公開API documentation不足
  - directory moveで二次時間になる完全diff再parse
- 追加finding: state validation、metadata parser、revision composition、process/evidenceの4件
- CI run #609、#639、#643はsuccessだが、現行5 testは上記の複合transition、certainty、settings、performance、malformed inputを検出しない
- AC-09、AC-10、AC-24およびT204終了条件を満たさないため承認不可

## 必要な修正

1. 全source file IDを変更前snapshotから解決し、transition graphを検証後に一括適用する
2. unresolved source/destinationを返却snapshot上で確実に未確認化するcontractを定義する
3. copy・split・merge・plain additionのdestinationを新規未確認stateとして表現する
4. 内容変更renameでは`contentHash`を更新または除去し、100% renameとの違いをtestする
5. old/new textをmapperへ渡し、whitespace/EOL設定のrename同時変更testを追加する
6. parsed diffを1回だけ生成し、file section単位でmappingする
7. lineCount・interval・state key/fileId・path一意性のvalidationを追加する
8. quoted path終端、duplicate metadata、conflicting statusのnegative testを追加する
9. chain、swap、delete+rename、copy、split、merge、addition、missing source、duplicate path、stale hashのtestを追加する
10. public APIへ完全snapshot、revision混在、unresolved、新規file、mutation、例外条件のJSDocを追加する
11. T204実装レポートと`tasks/tasks-status.md`を同期する
12. 修正後のPR HEAD SHAに紐づくfocused testと全CIを確認する
