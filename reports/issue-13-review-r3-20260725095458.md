### blocking: content hash変更時にbaseline metadataを更新せず、次のfallback追加を失う

対象:

- `src/adapters/document-review-state/reconciled-document-review-state-session-provider.ts:259-315`
- `doc/design/issue-13-document-context-routing.md:219-239`

`matchingBaseline`はsource identity、content hash、line countまで比較している。一方、その後の早期returnは、追加差分・解除差分が空で、前回snapshotと現在snapshotのintervalが同じかだけを確認する。

このため、intervalは同じだがcontent hash等のbaseline metadataが変化した場合、設計が要求する「intervalを変えずbaselineだけを記録する」を行わず、古いbaselineを残す。

再現可能な正常系:

1. content `H1`でworkspace sourceの範囲AをGitへ移行し、baseline `H1 / A`を記録する
2. ファイル内容が`H2`へ変わり、edit mapping未接続の現行仕様に従って両ownerの旧file stateを無効化する
3. Git ownerとworkspace fallbackの双方で、現在内容`H2`に対して同じ範囲Aを再度確認済みにする
4. Git復旧時、sourceとtargetのintervalは同じAだが、既存baselineは`H1 / A`のため`matchingBaseline`はfalseとなる
5. 早期returnがinterval Aの一致だけで成立し、baselineを`H2 / A`へ更新しない
6. 次のGit unavailable期間にworkspace側へ範囲Bを追加する
7. 復旧時も古い`H1 / A`はmatching baselineにならず、workspace contextの`createdAt`がGit file更新より古い場合はBを追加差分として適用しない
8. 現在source `H2 / A+B`をbaselineとして記録するだけで、Git ownerはAのままとなり、Bが以後の差分からも消える

これは設計7.4の「sourceと移行先のintervalが一致する場合はintervalを変えずbaselineだけを記録する」と、「次回以降の確実な差分だけを扱う」を満たさない。ユーザーがfallback側で行った確認済み追加が上位ownerへ反映されず、baselineだけが先へ進むため、後続openでも自動回復できない。

現在の再現test 2件はcontent hashが一定のまま、初回追加と上位owner解除後の追加だけを確認しており、このmetadata更新経路を固定していない。

修正状況: 未修正。

必要な対応:

- 先に、`H1 / A`のbaseline確立後、`H2 / A`へbaseline metadataだけを更新し、その後fallbackで追加したBがGitへ反映される再現testを追加する
- 早期returnをinterval一致だけで判定せず、source identity、content hash、line count、必要なsnapshot metadataを含む次baseline全体が現在baselineと一致するときだけ省略する
- `matchingBaseline`がfalseでsourceとtargetのintervalが一致する場合は、設計どおりbaseline更新transactionをcommitする
- 修正後、返却sessionと永続化済みbaselineの一致もtestで確認する

### 前回findingの確認結果

#### HEAD exit code 128分類

前回指摘は解消されている。

- `HEAD^{commit}`のexit code 128を一律missing扱いする処理は削除された
- C localeの`fatal: Needed a single revision`だけをunborn HEADとして受理する
- `fatal: bad object HEAD`等は`GitCommandFailedError`として伝播する
- 既知unbornと未知128を分離するtest自体も追加されている

ただし、前述のtest suite登録漏れにより、再レビュー対象headの最終CIではこのtestが実行されていない。

#### Git復旧時の基本reconciliation

前回指摘した基本ケースは実装上修正されている。

- 既存Git state Aと、後から作成されたfallback state BをA+Bへ統合する
- baseline確立後はfallback sourceの追加・解除deltaを計算する
- Git側で解除済みのAを古いfallback stateから単純unionで復活させない

ただし、content hash変更後のbaseline更新欠落が残るため、finding全体を解消済みとは判定しない。
