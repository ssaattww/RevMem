## Findings

### T402-R001 — High — content fallbackがGitと異なる変更行座標を返す

- Origin: introduced_by_change
- Location: `src/application/github-pr-diff/content-diff-builder.ts` `editOperations` / `hunksFromContents`
- Description: content fallbackは独自LCSを使用し、同長候補のtieで常にold側の削除を優先する。このalignmentはGit/GitHubのdiff alignmentと一致する保証がない。実装はadditions/deletions件数だけをGitHub file recordと照合するため、座標が異なっても件数が一致すれば完全なsnapshotとして成功する。
- Impact: PR進捗が実際とは異なる行を変更行として数える。ユーザーがGitHub上で変更された行を確認しても未確認のまま残る、または実際には変更された別の行を確認済みとして扱う可能性がある。これはT402の完全なPR差分と、確実な範囲だけを確認済みにする設計原則を破る。
- Evidence: old contentを`a\n`、new contentを`b\na\na\n`とすると、`git diff --no-index --unified=0`は`@@ -0,0 +1,2 @@`としてnew line 1と2を追加行にする。T402のLCSはnew line 1と3を追加行にする。どちらもadditions=2、deletions=0なので現在のstatistics checkを通過する。既存testは一意にalignmentできる内容だけで、重複行による座標差を検証していない。
- Required action: Git/GitHub PR diffと同じ座標意味論を提供するdiff engineへ置き換えるか、複数の最適alignmentが存在して座標を確定できない場合はfail-closedにする。上記の重複行fixtureをtest-firstで追加し、Git互換のchanged coordinatesを固定する。

### T402-R002 — High — GitHub status変換がtype changeとbinaryを正しく表現できない

- Origin: introduced_by_change
- Location: `src/adapters/github/fetch-github-pull-request-diff-adapter.ts` `statusFrom` / `parseFile`、`src/application/github-pr-diff/github-patch-diff-builder.ts` zero-change branch
- Description: `statusFrom`はGitHubの`changed`を`modified`へ変換する一方、`binary`というstatusを待ち受ける。GitHub公式`PatchStatus`では`CHANGED`はfile type変更であり、列挙値はADDED、CHANGED、COPIED、DELETED、MODIFIED、RENAMEDで、BINARYは存在しない。したがって標準API応答からこのadapterが`status: binary`を生成する経路はなく、type changeもcontent modificationへ潰される。さらにzero additions/deletionsかつpatch欠落のnonbinary recordを完全なpatch snapshotとして受理するため、binaryまたはtype-only changeの曖昧さを解消せず成功する。
- Impact: binaryがT301のbinary exclusionへ到達せず、`modified`または`added`の0行変更として扱われる。type changeも内容変更と区別されない。PR Progressの分類、除外理由、表示、後続diff editorの前提が不正確になり、implementation reportの「binaryは行単位レビュー対象外として保持する」という記述もremote経路では成立しない。
- Evidence: `statusFrom`は`case "changed": return "modified"`と`case "binary": return "binary"`を持つ。`buildSnapshotFromGitHubPatches`はnonbinaryのadditions=0/deletions=0について、patchが未定義でもhunks=[]で成功する。T301 unit testは`status: "binary"`のfileへbinary exclusion reasonを付けるが、T402 testには標準`changed`、patchless binary、binary exclusionへの接続caseがない。
- Required action: GitHubの標準status意味論を契約へ反映し、type changeを`modified`へ推測変換しない。binaryはstatus文字列ではなく信頼できるcontent/blob metadata等で分類するか、分類不能ならsnapshotを返さない。patchless zero-stat recordを曖昧なまま完全とみなさないtestを先に追加し、true binaryがbinary exclusionへ到達することを検証する。

### T402-R003 — Medium — pure copyが追加fileとして計上される

- Origin: introduced_by_change
- Location: `src/adapters/local-git/local-git-pull-request-diff-adapter.ts` `git diff` arguments
- Description: local routeは`--find-copies`を指定するが`--find-copies-harder`を指定しない。Git公式diff optionsでは、通常の`--find-copies`は同じchangesetで変更されたsource fileだけをcopy元候補にし、未変更fileをcopy元として調べるには`--find-copies-harder`が必要とされる。
- Impact: 未変更fileを複製した一般的なcopyが`copied`ではなく`added`として取得され、local routeが最初に成功するためGitHub routeへ進まない。pure copyの全行が追加変更行としてPR進捗の分母へ入り、copy metadataと0-hunkの非行変更が失われる。
- Evidence: baseに`source.txt` (`a\nb\nc\n`)をcommitし、headで同内容の`copied.txt`だけを追加した再現では、現在と同じ`git diff --find-renames --find-copies`は`new file mode`と3追加行を出力した。`--find-copies-harder`では`similarity index 100%`、`copy from source.txt`、`copy to copied.txt`となりhunkはない。T402 testはmock command引数だけで、実repositoryのcopy検出を検証していない。
- Required action: pure copyの期待意味論と性能上限を明示し、temporary Git repositoryを使うintegration testをtest-firstで追加する。copyをT402で扱う契約を維持するなら、未変更sourceも含む検出を安全な上限付きで実装する。扱わない判断なら、`copied`対応表明とsnapshot contractを同時に見直す必要がある。

### T402-R004 — High — paginationがrequest数を拘束せず、page欠落も受理する

- Origin: introduced_by_change
- Location: `src/adapters/github/fetch-github-pull-request-diff-adapter.ts` `nextPage` / files取得loop
- Description: next Linkはorigin、protocol、path、credential、fragmentだけを検証し、page番号、`per_page`、追加query、前pageとの単調性を検証しない。loopの上限は蓄積file数3000件だけであり、request/page数の上限がない。
- Impact: 空配列と毎回異なるnext URLを返すAPI/proxyに対してfile数が増えず、visited URLも重複しないためrequestが終了しない。page 1からpage 3へのLinkも受理され、page 2の変更fileを欠落させた一覧を完全として返す。前者はExtension Hostの処理停止、後者は変更fileをPR進捗の分母から消して誤った完了率を生成する。
- Evidence: `while (true)`はvisited exact URLと`files.length >= 3000`だけで停止する。`nextPage`は同一collection pathなら任意queryを許す。既存pagination testはpage 1から2の正常系だけで、空page連鎖、page jump、`per_page`変更、request上限を検証していない。implementation handoffの「bounded, validated pagination」という記述と実装が一致しない。
- Required action: client側で期待pageを管理するか、next URLを`page = previous + 1`、固定`per_page=100`、許可queryのみへ制限する。GitHubの3000-file capに整合する明示的な最大request数を設け、空pageにnextがある場合、page jump/regression、query改変、上限超過をfail-closedにするtestを追加する。
