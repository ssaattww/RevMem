## レビュー観点

- workspace membershipよりGit ownershipが優先されること
- Git unavailableから復旧した場合も、fallback ownerで追加された確実な確認済み範囲を失わないこと
- owner昇格時にcontent hashとline countが一致する確実な範囲だけを移行すること
- Gitの明示的な非repositoryまたはunborn状態だけをfallback・missing HEADとして分類すること
- 権限、timeout、破損repository等のGit失敗を正常状態へ誤分類しないこと
- UNC authorityとWindows filesystem semanticsがidentityから消えないこと
- external-file、workspace、Git repositoryの保存先とcontext kindが混線しないこと
- context/Globalがatomicに更新されること
- decoration readが状態を作成・変更しないこと
- 既存workspace、Git、PR persistence contractを壊さないこと

## 検出・修正事項

### blocking: Git復旧時にfallback ownerで追加した範囲が昇格されない

対象:

- `src/adapters/document-review-state/document-review-state-session-provider.ts:625-630`
- `doc/design/issue-13-document-context-routing.md:47-54`
- `doc/design/issue-13-document-context-routing.md:180-221`

`promoteFirstCertainSource`は、移行先のcontextまたはGlobalに対象file stateが1件でも存在すると、移行元を確認せず即座に`targetSession`を返す。

このため、次の正常系でfallback owner側の追加確認がGit ownerへ反映されない。

1. Gitが利用可能な状態でGit ownerへ確認済み範囲を保存する
2. Git executableが一時的に利用不能となり、workspaceまたはexternal-file ownerへfallbackする
3. fallback ownerで別の範囲を確認済みにする
4. Gitが復旧し、同じHEAD、content hash、line countでGit ownerを再度解決する
5. Git ownerには既存file stateがあるため、fallback ownerの追加範囲を読み込まず終了する

旧ownerの状態自体は残るが、高いownerが利用可能な間は表示・書き込みに使われないため、ユーザーからは追加確認が失われたように見える。設計3.1の「後からGit ownershipを解決できた場合は7章の移行規則を適用する」と、7章のowner昇格要件を満たさない。

既存testは移行先が空の`external-file -> workspace`および`workspace -> Git`だけを確認しており、移行先に既存範囲がある復旧ケースを固定していない。

修正状況: 未修正。

必要な対応:

- 先に、移行先に既存範囲がある状態でfallback側に追加範囲が存在する再現testを追加する
- content hash、line count、revision certaintyを満たす場合のreconciliation規則を定義する
- 追加操作だけでなく、fallback側で解除された範囲をどう扱うかを明示し、単純unionで解除を復活させないこと

### blocking: HEAD確認の任意のexit code 128をunborn branchとして扱う

対象:

- `src/adapters/local-git/local-git-adapter.ts:79-80`
- `src/adapters/local-git/local-git-adapter.ts:289-301`
- `doc/design/issue-13-document-context-routing.md:56-58`

`resolveHead`は`git rev-parse --verify HEAD^{commit}`の終了コードが1または128なら、stderrの内容を確認せず`undefined`を返す。呼び出し側はこれをunborn branchとして扱い、`unborn:<branch-ref>`を現在revisionにする。

終了コード128はunborn branchだけでなく、破損したHEAD、object databaseの異常、アクセス失敗等でも返り得る。これらを正常なunborn状態へ誤分類すると、設計3.2が要求するエラー伝播を行わず、実在しないunborn revisionへ新しいレビュー状態を初期化し得る。

PRで追加された回帰testは`rev-parse --show-toplevel`の明示的な`not a git repository`診断だけを確認している。`HEAD^{commit}`について、既知のunborn診断と予期しない128エラーを分離するtestはない。

修正状況: 未修正。

必要な対応:

- 先に、既知のunborn HEAD診断だけをmissing HEADとして受け入れるtestを追加する
- 破損repositoryまたは予期しないexit code 128を`GitCommandFailedError`として伝播するtestを追加する
- `isMissingValueExit`をHEAD確認へ無条件適用せず、commandごとの期待結果を分類する
