## 検出・修正事項

### blocking: 新しいGit contextの初期化がrepository-wide Global stateを空へ置換する

対象:

- `src/adapters/state-repository/file-system-review-state-repository.ts:329-386`
- `src/adapters/state-repository/file-system-review-state-repository.ts:409-473`
- `src/adapters/state-repository/coherent-file-system-review-state-repository.ts:219-260`
- `src/adapters/document-review-state/document-review-state-session-provider.ts:301-318`
- `doc/design/document-context-routing.md:143-179`
- `doc/design/document-context-routing.md:216-227`

repository-style storageのmanifestは複数contextと1つのowner-wide Global stateを保持する。一方、対象`contextId`がmanifestに存在しない場合、low-level loadはmanifestのGlobal stateを読み込まず`undefined`を返す。

その結果、次の正常系で既存Global stateが失われる。

1. branch A contextでGlobal確認済み範囲Gを保存する
2. 同じRepository IDのbranch Bへ切り替える
3. branch BのContext IDはmanifestにまだ存在しないため、repository loadが`undefined`を返す
4. document providerはrepository全体が未初期化された場合と区別できず、branch B用の空contextと`files: {}`の空Global stateを生成する
5. repository `save`は既存context referenceを保持するが、manifestのGlobal referenceをbranch Bの空Global documentへ置換する
6. branch Aで保存されていたGがrepository-wide Global stateから消える

これはbranchだけでなく、新しいdetached HEAD contextまたは将来のpull-request contextでも同様に発生する。

さらにbranch Aへ戻ると、branch A context descriptorとbranch B由来のGlobal `currentRevisionId`が組み合わされ、revision mapping未接続の現状ではsessionを再度開けなくなる可能性がある。

設計6.5の「snapshotがなければ空のcontext stateとGlobal stateを初期保存する」は、repository manifest自体がない場合と、repositoryは存在するが対象contextだけがない場合を区別していない。owner-wide Globalを持つ設計と矛盾する。

修正状況: 未修正。

必要な対応:

- repository未作成とcontext未作成を区別する
- context未作成時は既存manifestが指すGlobal stateを読み込み、新contextだけを追加する
- revisionが異なりmappingできない場合は、既存Globalを空で上書きせず、mapping要求または保守的な拒否として扱う
- branch AでGlobal rangeを保存後、branch Bを初回openしても既存Global documentを破壊しないfilesystem integration testを追加する
- branch B作成後にbranch A contextとGlobal stateを再度読み込めることを確認する

### blocking: lower owner contextの再作成を明示的な全解除として扱う

対象:

- `src/adapters/document-review-state/reconciled-document-review-state-session-provider.ts:328-382`
- `src/adapters/workspace-review-state/workspace-review-state-session-provider.ts:235-304`
- `src/core/contracts/review-state.ts:149-187`
- `doc/design/document-context-routing.md:297-333`

baseline snapshotは`sourceCreatedAt`を保存し、同一snapshot判定でも比較している。しかし、追加・解除deltaを計算する`matching`判定はsource owner、Repository ID、Context ID、File ID、content hash、line countだけを比較し、`sourceCreatedAt`を比較しない。

workspaceとexternal-fileのRepository、Context、File IDはdescriptorから決定的に生成される。したがってlower owner stateを削除して同じresourceで再初期化すると、IDは同じまま`createdAt`だけが新しくなる。

再現可能な経路:

1. workspace sourceで範囲Aを確認し、Git targetへAとworkspace baselineを保存する
2. workspace保存stateを削除またはリセットする
3. Git unavailable中に同じworkspaceを再初期化する。Context IDとFile IDは以前と同じだが`createdAt`は新しい
4. 再作成直後のworkspace stateは対象fileが空、または別範囲Bだけを持つ
5. Git復旧時、旧baselineはID、hash、line countが一致するためcommon baselineとして扱われる
6. 旧baseline Aと現在sourceの差分が明示的removalとして計算され、Git側のAを解除する

lower owner storageの消失・再作成はユーザーによるAの解除操作ではない。source contextのincarnationが変わった場合は旧baselineとの解除差分を適用してはならない。

修正状況: 未修正。

必要な対応:

- common baseline判定へ少なくとも`sourceCreatedAt`を含める
- source incarnationが変化した場合はbaselineなしの保守規則へ戻し、既存target rangeを推測解除しない
- source state削除後に同じworkspace/external-file contextを再作成する回帰testを追加する
- 再作成された空sourceがtargetの既存rangeを解除しないことを確認する
- 再作成sourceで新たに確認したrangeは、安全なadditionとして扱える条件を明示する

### blocking: reconciliation metadataのreviewed intervalがlineCount外でも永続化validationを通過する

対象:

- `src/adapters/state-repository/owner-reconciliation-validation.ts:30-95`
- `src/adapters/state-repository/validated-file-system-review-state-repository.ts:15-57`
- `src/core/review-state/review-state-service.ts:215-228`
- `doc/design/document-context-routing.md:232-265`

metadata validatorは`lineCount`が非負のsafe integerであることと、各intervalの`endLineExclusive > startLine`を確認する。しかし、intervalがsnapshotの`lineCount`内に収まることを確認しない。

例:

```text
lineCount = 8
reviewed = [{ startLine: 7, endLineExclusive: 9 }]
```

このsnapshotはsaveとloadの両方を通過する。後に同じsourceとのbaseline deltaを計算すると、lineCount外のadditionまたはremovalがReview State Serviceへ渡り、そこで初めて`must stay within the current file line count`として失敗する。

設計はmalformed reconciliation metadataをpersistence errorとして拒否する契約である。現在は不正stateを永続化・読込でき、通常のdocument session openを後段のrange errorで停止させる。

既存testは負の`lineCount`だけを破損例としており、interval上限、0行fileの非空interval、lineCountとreviewedの整合性を確認していない。

修正状況: 未修正。

必要な対応:

- `validateSnapshot`で全intervalの`endLineExclusive <= lineCount`を検証する
- 必要ならintervalの正規化済み・非重複・昇順contractも明示する
- save、load、commitの各境界でlineCount外intervalを拒否するtestを追加する
- malformed stateがreconciliation planningへ到達しないことを確認する

## 追加確認事項

### repository `save`のcross-context stale Global上書き

`FileSystemReviewStateRepository.save`はstorage root単位でwrite順序を直列化するが、callerが渡したGlobal snapshotをCASまたは最新Globalとのmergeなしで保存する。

異なるcontextが同じGlobal G0を読み、それぞれGAとGBを作って順に`save`した場合、最後のsaveが先のGlobal更新を失わせる。前述の新context初期化はこの問題が競合なしでも発生する確定経路である。

新context初期化を修正する際は、owner-wide Globalを更新する`save`経路全体について、context追加・stale file sanitization・background saveが別contextの更新を上書きしないことも確認する必要がある。

### held: `objectExists`のexit code 128分類

R5から継続。

- `LocalGitAdapter.objectExists`はexit code 1または128をmissing objectとして扱う
- revision mapping側の既存責務であり、このPRのowner routing/reconciliation正常系では使用しない
- 既存revision mapping担当変更でcommand固有の診断分類を追加する
