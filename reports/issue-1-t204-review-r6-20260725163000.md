## Blocking findings

### 1. unchanged fileの非正規化`modifiedReviewed`を正常なcomplete snapshotとして返せる

`validateStateSnapshot`は`normalizeLineIntervals(file.modifiedReviewed)`の結果について境界だけを確認するが、入力配列が正規化済みであることを検証せず、正規化結果をstateへ戻してもいない。

そのため、例えば次の入力を受理し得る。

- overlapping interval
- adjacent intervalが未結合
- 順序が逆
- 空interval
- 重複interval

対象fileがdiffで変更されない場合、`active`には`cloneState`した元の非正規化配列がそのまま残る。結果は「detached complete snapshot」を名乗るが、既存のinterval contractに従わないstateを正常returnする。

影響:

- 後続の進捗計算や範囲解除が、正規化済みintervalを前提にすると二重計上・検索不整合を起こし得る
- persisted state破損をtransition境界で検出できない
- changed fileだけが偶然`mapReviewed`で正規化され、unchanged fileと挙動が不一致になる

必要対応:

- 全`modifiedReviewed`が既にcanonicalであることを厳密比較で検証して拒否する、または
- complete snapshot生成時に全fileをcanonical stateへ正規化する
- overlapping、adjacent、unsorted、empty、duplicateの回帰testを追加する

### 2. `originalReviewedByDiff`が完全に未検証で、壊れたoriginal-side stateを伝播する

`cloneState`は`originalReviewedByDiff`を深いコピーするが、`validateStateSnapshot`はその各diff IDとinterval配列を一切検証していない。

少なくとも次の不正値を通過させ得る。

- 空diff ID
- negative line
- reversed / empty interval
- `NaN`、`Infinity`、非safe integer
- overlapping / duplicate / unsorted interval

original側line countはfile-level `lineCount`と別であるため上限境界を検証できない場合でも、数値の有限性、非負性、半開区間、canonical ordering、diff ID非空は検証可能である。現状は変更対象外fileだけでなくrename後stateにも壊れたoriginal-side stateが残り得る。

影響:

- T303以降のoriginal側確認・削除行進捗で不正rangeが表面化する
- JSON由来の`NaN`は通常ないが、application内入力やmigration途中stateではruntime boundaryとして防げない
- complete snapshot contractとAC-24の「不確実な範囲を確認済みにしない」に反する

必要対応:

- `originalReviewedByDiff`のkeyと全intervalを検証する共通validatorを追加する
- 上限を検証できない場合も、有限safe integer、0以上、`start < end`、canonical orderingを必須とする
- invalid original intervalと空diff IDの回帰testを追加する

## Medium findings

### 3. `FileReviewState`のruntime contract検証が部分的すぎる

現在検証されるのは主にkey/fileId一致、currentPath一意、lineCount、`modifiedReviewed`境界だけである。persisted stateを受け取るpublic boundaryとして、少なくとも以下が未検証である。

- `schemaVersion`が対応versionか
- `fileId`、`revisionId`、`updatedAt`が非空・妥当か
- `previousPaths`の空文字、重複、`currentPath`との重複
- `contentHash`の空文字

すべてをT204で厳密化する範囲かは整理が必要だが、少なくともunsupported schemaを黙って返すのはmigration boundaryを迂回する。

### 4. authoritative parserと事前validatorの二重section/path解析が残っている

R3〜R5で実際に複数回、TAB suffix、rename metadata、`/dev/null` sideの仕様差が発生した。現在もvalidatorとunderlying parserが別々に以下を実装している。

- section split
- quoted path decode
- metadata path decode
- header path decode
- status classification

今回の修正自体は動作しているが、今後のGit diff形式追加で再び片側だけ更新される可能性が高い。parse結果へstatus validationとdestination uniquenessを統合し、公開関数が一つのauthoritative parsed modelだけを利用する構造が望ましい。
