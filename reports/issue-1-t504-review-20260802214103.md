## 7. 指摘事項

### T504-R1-P1: hash evidence欠落時にGlobal stateをcurrent扱いし、変更済み行を分子へ算入できる

- Severity: **high**
- Origin: introduced_by_change
- Location: `src/core/global-understanding/global-understanding-progress.ts` の `isCurrentGlobalFile()`
- Description:
  - pathとrevisionが一致した後、`snapshot.contentHash === undefined || globalFile.contentHash === undefined || hash一致`をcurrent条件としている。
  - このため片側のhashが欠落すると、hash不一致を検出できないにもかかわらずcurrentとなる。
  - Node sourceは現在のworking tree bytesから必ずSHA-256を生成する一方、T501の公開contractとstate serviceは`GlobalFileReviewState.contentHash`をoptionalとしており、hashなしGlobal stateを正規に保持できる。
- Impact:
  - 同じpath/revision labelのままcurrent file bytesが変化し、Global側hashが欠落している場合、以前のreviewed intervalが現在も有効である証拠がないのに非空行を確認済みとして算入する。
  - Global理解率が実際より高く表示される。これは設計のcertainty-firstと、実装handoffに記録された「current revision/path/content evidenceが一致しないGlobal stateは分子へ寄与しない」に反する。
- Evidence:
  - `GlobalFileReviewState.contentHash?: string`はoptional。
  - review state serviceはtarget hashがない場合、次のGlobal stateへhashを書かない。
  - T504 testはhash一致とhash不一致を確認するが、snapshot hashあり/Global hashなし、および逆方向を確認していない。
- Required action:
  1. 片側hash欠落のRed testを先に追加する。
  2. exact current-file hashがある経路では、Global側hashが存在して完全一致する場合だけcurrentとする。欠落・不一致はstaleとして分子0にする。
  3. revision-only evidenceを許容する別経路が必要なら、暗黙のoptional判定ではなくsource/evidence種別を明示したcontractへ分離し、certainty条件をtestで固定する。

### T504-R1-P2: 空fileのline countがeditor/state contractとずれ、current Global rangeでrepository再計算全体が失敗する

- Severity: **medium**
- Origin: introduced_by_change
- Location:
  - `src/adapters/repository-files/node-global-understanding-file-source.ts` の `splitLogicalLines()`
  - `src/core/global-understanding/global-understanding-progress.ts` の `normalizeReviewed()`
- Description:
  - Node sourceは0 byte fileを`[]`へ分割し、`lineCount: 0`を返す。
  - 一方、VS Code `TextDocument`の空documentは1 logical lineとして扱われ、T501のnormal editor操作は`lineCount: 1`で`[0,1)`のGlobal reviewed intervalを正規に作成できる。
  - そのGlobal entryと空fileのhash/revision/pathが一致するとT504はcurrent判定後に`[0,1)`を`lineCount: 0`へvalidateし、RangeErrorを投げる。
- Impact:
  - 空file自体は非空行0でGlobal理解率へ0/0として安全に寄与できるはずだが、1つの空fileにcurrent Global状態があるだけでbackground recalculation全体がrejectされる。
  - T504のfile/repository calculatorが通常操作で生成可能なT501 stateを処理できない。
- Evidence:
  - 既存T504 testのempty snapshotはGlobal entryを持たないため`normalizeReviewed()`へ到達しない。
  - Node source testも空file/current Global stateの組合せを確認していない。
- Required action:
  1. 実際の0 byte fileをNode sourceで読み、matching current Global `[0,1)`をcalculatorへ渡すRed testを追加する。
  2. current-file line countをT501/VS Code側のlogical line semanticsと統一し、空fileは`lineCount: 1`、`nonEmptyLines: []`として扱う。
  3. T503の分母候補`nonEmptyLineCount: 0`との整合を回帰testで固定する。

### T504-R1-P3: file数だけのchunk分割では単一大fileの同期scan/hashを分割できず、終了条件の応答性を保証しない

- Severity: **medium**
- Origin: introduced_by_change
- Location:
  - `src/application/global-understanding/global-understanding-background-recalculator.ts` のchunk loop
  - `src/adapters/repository-files/node-global-understanding-file-source.ts` のdecode、line scan、SHA-256計算
- Description:
  - `yieldControl()`は非final chunkの完了後だけ呼ばれる。
  - 各fileの`Buffer.toString("utf8")`、全体split、全行trim scan、全Buffer hashは同期処理である。
  - includedが1 file、または大fileがfinal chunkにある場合、処理途中にcooperative yieldは存在しない。
- Impact:
  - 大きな単一source fileでExtension Host event loopを長時間占有できる。
  - 「chunk処理を実装した」ことは確認できるが、T504終了条件の「event loopを長時間占有しない」をfile-sizeに依存せず満たす証拠がない。
- Evidence:
  - focused testは4つの小fixtureを2-file chunkへ分け、chunk間yield回数だけを確認している。
  - 単一大file、final chunk内のwork budget、scan中yieldを確認するtest・計測がない。
- Required action:
  1. 単一大fileでもbounded work/yieldが観測できるRed testまたは決定的scheduler testを追加する。
  2. line/hash処理をstreamまたはbyte/line chunkへ分割し、一定work量ごとにcooperative yieldする。
  3. 別案としてfile-size上限による明示的除外を採用する場合は設計変更として定義し、除外診断と分母契約を更新する。暗黙にT607へ先送りしない。

### T504-R1-P4: implementation handoffがrequired schema v3ではなく、current-head review transferをlosslessに表現していない

- Severity: **low**
- Origin: introduced_by_change
- Location: `reports/issue-1-t504-handoff-20260802211500.yaml`
- Description:
  - handoffは`schema_version: 1`で生成されている。
  - 現行handoff contractはwriterがschema version 3を使用し、identity、target/current/reviewed head、permissions、validation、findings、unknowns、next action、raw source payloadsをtypedかつlosslessに保存することを要求する。
  - v1 reader compatibilityは旧artifact読取用であり、新規writerがv1を出力する根拠ではない。
- Impact:
  - review/fix workerへの権限、reviewed/current headの区別、finding continuity、validation/unknownsが標準fieldで引き継がれず、後続workerが本文解釈へ依存する。
- Required action:
  - T504修正handoffをschema v3で再生成し、新しいimplementation HEAD、exact-head CI、TDD evidence、finding IDs/severity、permissions、remaining risks、raw source payloadsを保存する。
