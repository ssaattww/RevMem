## Findings

### R60-001 — High — immutable PR HEAD scan is gated by the mutable working-tree path set

- Origin: introduced by PR #60.
- Locations:
  - `src/t505-global-understanding-source.ts`: `recalculate()`, `capturePullRequestHeadFiles()`.
  - `src/t405-pull-request-review-runtime.ts`: `readGlobalHeadFiles()`.
- Description:
  - `T505GlobalUnderstandingSource.recalculate()` builds `candidatePaths` by walking `owner.repositoryRoot`, i.e. the mutable working tree.
  - `PullRequestReviewRuntime.readGlobalHeadFiles()` skips every HEAD-side PR file for which `candidatePaths.has(file.newPath)` is false.
  - `capturePullRequestHeadFiles()` performs the same candidate-set gate again, and the final `openedByPath` projection filters retained evidence through the same mutable candidate set.
  - Current-PR selection proves only that persisted PR `headSha` equals the local Git HEAD object. `findCurrentPullRequestContext()` does not require a clean working tree.
- Impact:
  - With local HEAD equal to the PR HEAD, an unstaged/uncommitted deletion or rename of a file that still exists in the immutable PR HEAD makes the filesystem enumerator omit that path. The PR full scan then silently skips the file even though the exact commit blob remains available through `readTextFileAtRevision()` / GitHub fallback.
  - Global opened-file count and line denominator can therefore omit a reviewable PR file and depend on dirty-worktree state rather than the accepted immutable PR revision.
  - This violates the PR #60 contract that reviewable PR files are fully scanned from HEAD/BASE when that PR is the active context.
- Test gap:
  - The new T405 full-scan test passes a candidate set that already contains every modified/HEAD-side file.
  - The new T505 PR-source test likewise asserts that the working-tree candidate set contains the PR file. Neither regression covers an immutable HEAD file that is absent from the mutable working tree.
- Required action:
  - Decouple the immutable PR file universe from mutable working-tree path existence. For active PR Global calculation, derive reviewable HEAD-side files from the validated PR snapshot plus exclusion policy and read them from the exact HEAD regardless of uncommitted filesystem deletion/rename.
  - Adjust the T505 candidate/opened/unopened projection so immutable PR HEAD evidence is not discarded solely because the mutable path walk omitted the path.
  - Add a TDD regression where a PR snapshot contains a HEAD-side file but the mutable `candidatePaths` set does not; assert the exact HEAD file is still read, promoted, and counted.

### R60-002 — Medium — rev4 design remains authoritative but contradicts the new Global denominator contract

- Origin: introduced by the accepted Issue #59 behavior but left undocumented by PR #60.
- Location: `doc/design/vscode-review-range-tracker-design.md` §11.3 and §12; no corresponding PR change or explicit override in `Design/BreakingChanges.md`.
- Description:
  - Rev4 §11.3 still defines `Global理解率 = 現在有効なGlobal確認済み非空行数 / 対象全非空行数` and says repository `included` entries carry each file's non-empty line count into the denominator.
  - §12 still describes binary/fatal-UTF-8 files as excluded after repository enumeration/content classification.
  - PR #60 intentionally changes ordinary Global semantics to opened/retained evidence only, reports unopened paths separately, and deliberately avoids content-classifying unopened files.
- Impact:
  - The accepted implementation and the repository design contract now describe different denominators and exclusion/classification semantics. A later implementation or review following rev4 can legitimately reintroduce the repository-wide scan that Issue #59 removes.
- Required action:
  - Update the authoritative design to define the opened/retained denominator, opened/unopened diagnostics, deferred classification of unopened content, and the active-PR immutable full-scan exception; or, if rev4 must remain unchanged, record an explicit superseding policy in the repository's breaking-change mechanism and reference it from the implementation report.

### R60-003 — Medium — T505 retains obsolete revision evidence for the entire Extension Host lifetime

- Origin: introduced by PR #60.
- Location: `src/t505-global-understanding-source.ts` fields `openedEvidenceByOwner` / `pullRequestEvidenceByOwner`, `ownerEvidenceKey()`, `retainedOpenedEvidence()`, `capturePullRequestHeadFiles()`, and `setContext()`.
- Description:
  - Both evidence maps are keyed by serialized owner target plus exact revision.
  - Every new branch/PR revision therefore creates new retained maps.
  - There is no eviction when context/revision changes, no size bound/LRU, and `setContext()` only replaces `currentContext`.
  - PR full scans retain parsed `nonEmptyLines` evidence in `pullRequestEvidenceByOwner` and also copy it into `openedEvidenceByOwner`, so superseded revisions remain reachable until Extension Host termination.
- Impact:
  - Long-lived sessions with repeated commits/PR HEAD updates accumulate obsolete per-file line-index arrays and hashes. Large PRs can make this growth material, which conflicts with Issue #59's purpose of reducing Global Understanding resource load.
  - The T405 raw-text cache correctly invalidates on BASE/HEAD change, but T505's parsed/retained revision caches do not.
- Required action:
  - Evict superseded revision evidence for a stable owner identity, or apply an explicit bounded cache policy. Clean both T505 maps consistently on revision replacement/context lifecycle changes.
  - Add a regression that advances the same owner to a new HEAD and verifies obsolete parsed/retained evidence is no longer retained/reused.
