## 指摘事項

- 指摘要約: High 2件、Medium 5件、Low 3件
  - **High-1・blocking conservative correctness / runtime discriminant** — `src/core/pr-progress/pr-diff-progress.ts:151-190`は`line.kind === "context"`と`=== "deletion"`だけを分岐し、それ以外を無条件にadditionとして処理する。TypeScript型を外れた`"metadata"`、将来追加されたkind、破損cache値でも、`oldLine`がなく`newLine`と`file.additions`が一致すれば実additionとして算入される。外部API・cache由来のruntime inputを検証するboundaryでunknown kindを推測するため、`switch`のdefaultでrejectしなければAC-24を満たさない。同様に`file.status`も既知unionかruntime検証せず、未知statusを非binaryの通常fileとして保持する
  - **High-2・blocking incomplete/malformed patch correctness** — `src/core/pr-progress/pr-diff-progress.ts:135-243`はzero-zero hunkを拒否するが、`oldCount=1,newCount=1,lines=[context oldLine=1,newLine=1]`のようにaddition/deletionを1行も含まないcontext-only hunkを受理する。addition/deletion setとGitHub統計値がともに0なら、変更fileのhunkが存在するにもかかわらず`totalLineCount=0`、`progress=1`となる。Git unified diffのhunkは少なくとも1つの追加または削除を含むため、truncated parser output・破損cache・adapter不具合をmetadata-only/確認完了として扱わず、hunk単位で変更行0をrejectする必要がある
  - **Medium-1・blocking classification/path contract** — `src/core/pr-progress/pr-diff-progress.ts:254-257,281-300`はstatusとold/new path・line統計の組合せを検証しない。例えば`status="deleted"`なのに`newPath="generated/a.ts"`を持つ入力では`newPath`を表示・除外pathとして選び、user globにより本来の削除行を分母から外せる。`added`、`deleted`、`modified`、`renamed`、`copied`、`binary`ごとにpath presenceとline-data contractをsnapshot builderまたはcalculator boundaryで固定しないと、T304の分類・表示・除外判断が誤る
  - **Medium-2・blocking duplicate-file aggregation** — `src/core/pr-progress/pr-diff-progress.ts:276-300`はduplicate `fileId`だけを拒否し、正規化後の表示path重複を拒否しない。異なるfile IDで`./src/a.ts`と`src/a.ts`、または同じnew pathを2件渡すと、同じ変更fileを2回集計してTreeにも重複行を返す。T402のpagination/cache結合やfile ID生成不具合を保守的に検出するため、status/sideを考慮したcanonical path uniquenessが必要
  - **Medium-3・blocking persisted-state consistency** — `src/core/pr-progress/pr-diff-progress.ts:315-329`はstateの`fileId`と`revisionId`を検証するが、`FileReviewState.lineCount`と`modifiedReviewed`の上限、`currentPath`との整合を確認しない。contract上`lineCount`はmodified/current fileの現在行数であるため、`lineCount=1`、`modifiedReviewed=[99,100)`、line 100のadditionというsame-revision破損stateでも確認済みとして算入できる。少なくともlineCountを非負safe integerとして検証し、modified intervalのendがlineCountを超える状態はrejectする必要がある
  - **Medium-4・blocking TDD regression / inaccurate report** — `test/unit/pr-diff-progress.test.ts`はR4 regressionsを復元した一方、R3で追加したcontext ID mismatch、non-canonical originalDiffId、additionのopposite-side座標、context座標不一致、hunk gap/order、duplicate actual coordinateのtestを再び削除している。`reports/issue-1-t301-implementation-20260725094000.md:76-89`はこれらを現在のテスト対象として列挙しており、suiteと証跡が一致しない。レビュー対応のたびに既存regressionを置換せず、全findingを累積suiteとして保持する必要がある
  - **Medium-5・blocking submission evidence** — PR本文のTDD/evidenceはR3までで、R4 test-first `f65c3b7...`、failure run `30144870515`、implementation `91e52fd...`、Green/current head runsを記録していない。implementation reportはR4まで更新済みだがPR本文と提出状態が一致せず、現HEADの再現証跡として不完全である
  - **Low-1・held identifier validation** — `contextId`、base/head SHA、file IDを非空としてruntime検証しないため、空identityとcanonical `".."`の組合せでもcontext側が同値なら通る。通常adapterでは発生しないが、validated snapshot contractとしてnon-empty identityを明示する余地がある
  - **Low-2・held numeric boundary** — file単位の`additions + deletions`、aggregate加算、hunk anchor/end、cumulative deltaについてderived safe integerを再検証しない。通常のPR規模では到達しないが、pure APIが返すcountとratioの精度保証としてoverflow拒否が未対応
  - **Low-3・held performance/robustness** — reviewed intervalを1行ずつSetへ展開するため、変更行が少なくても巨大・破損intervalでExtension Hostを長時間占有できる。T607/T603/T606と重なるが、changed coordinateをinterval検索する方式なら入力全行展開を避けられる
- R4 finding disposition:
  - R4 High-1「zero-count hunk anchorとfirst-hunk delta」はanchor正規化とcumulative delta検証へ変更され、valid addition/deletion後のlater hunk testも通るためclose可能
  - R4 Medium-1「state payload file ID mismatch」は`state.fileId`照合追加によりclose可能
  - R4 Medium-2「削除された回帰test」はR2由来の統計値、non-PR、stale revision、duplicate file ID、binary exclusionを復元した。ただしR3由来testを削除したためpartial close
  - R4 Low「zero-zero hunk」は明示拒否されclose可能
  - safe integerと巨大intervalは未対応のheld concernとして継続
- 追加確認でfindingなし: zero-count hunk anchor正規化、first hunkからのcumulative delta、valid later hunk、state payload identity、zero-zero拒否、R4 test-first failure/Green evidence、current-main merge ref CIには上記以外の問題を確認しなかった
