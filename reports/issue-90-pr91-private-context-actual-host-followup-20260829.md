## 指摘事項

- 指摘要約または「指摘なし」:
  - exact command path: user logの`Review Contextsを更新`はUI wrapper `runOperation`の共通labelである（`vscode-review-contexts-runtime.ts:302-324`）。したがって、`reviewRange.refreshReviewContexts`／activation refreshの`T405ReviewContextsSource.load`→`readSynchronizedRepository`→lifecycle fetch（`:401-407`→`:979-993`）か、`reviewRange.redetectPullRequest`の`mutate`→interactive search（`:335-338`→`t405...:1094-1161`）のどちらでも同じlabelになる。前後logだけではこの二者を確定できない。`reconnectGitHub`は`:1166-1172`でsession取得だけを行いPR REST/このdiagnosticを生成しない。Current Contextの直接operation labelは別の`Current Contextを更新/選択`であるため、最初のERRORの直接labelではない。
  - HTTP/diagnostic: search adapterはtokenが存在する場合だけAuthorizationを付ける（`fetch-github-pull-request-adapter.ts:139-145`）が、`401/403`は`authentication`、rate-limit以外の非2xx（private repositoryでtoken無し・権限不足tokenの双方が取り得る`404`を含む）は`api`へ畳む（`:161-167`）。lifecycle adapterも同じく`404`を`api`へ畳む（`fetch-github-pull-request-lifecycle-adapter.ts:35-42`）。`OperationDiagnosticError`はallowlistの`reason`だけを保持・出力するため（`operation-feedback.ts:49-56,405-418`）、現行logの`reason=api`からtoken absent/present、HTTP status、account preference、retry有無は復元不能である。
  - VS Code auth semantics: current providerはGitHub.comなら`github`、それ以外は`github-enterprise`を選び、Enterpriseは`github-enterprise.uri`のcanonical authorityと一致する場合だけ許可する（`vscode-github-authentication-provider.ts:13-31,41-55`）。scopeは全callerで`["repo"]`（`t405...:663-666`）。background lifecycle/diff callersは`interactive=false`（`:750,845,937,980`）、redetectだけが`true`（`:1094`）で、providerは`{ createIfNone: interactive }`だけを渡し全session例外を`undefined`へ握りつぶす（provider`:51-61`）。
  - local VS Code typingsは、`createIfNone`を「matching sessionが無い／extension access未許可の場合にsign-in/consentを促す」option、`forceNewSession`を既存sessionがあっても再認証するoption、`clearSessionPreference`をmulti-account providerで既存preferenceを消してaccount選択を促すoptionと定義する。preferenceはextension単位かつworkspace/globalに保存される。`getAccounts`とaccount指定`getSession`は存在するが、current `VsCodeAuthenticationLike`には公開されていない。従って`createIfNone:true`単独は既存preferred sessionをclearせず、private repository accessを保証しない。
  - reconnectとの差分: source上の`reconnectGitHub`も`getSession(providerId, ["repo"], { createIfNone: true })`であり、`forceNewSession`も`clearSessionPreference`も使わない（`t405...:1166-1172`）。よってredetectとreconnectの画面差をoption差としては説明できない。一方、redetect providerはgetSession rejection/cancellation/provider failureを`undefined`へ握りつぶしてanonymous fallbackへ進むのに対し、reconnectは直接awaitする。実機でreconnect後にprivate PR候補が表示された事実は、VS Code session/consent/preferenceがその間に回復・確定したことを支持するが、wrong preferred account、session/consent未成立、scope不足のどれかはaccount/session観測がないため未確定である。
  - privacy-safe diagnostic候補: raw token/account/repositoryを追加せず、`GITHUB_PR_DETECTION_UNAVAILABLE`へallowlisted `token: absent|present`、`http: 401|403|404|other`、`interactive: none|create|reselect`、`retry: none|reselect-attempted`のenumだけを持たせる。adapterはstatus classを安全に返し、compositionはtoken presenceとuser-explicit retryを加える。これにより`404`のanonymous fallback、tokenありaccess不一致、reselect後failureを区別できる。
  - root cause classification: **確定**はprivate targetへVS Code pathが`reason=api`でfail-openし、reconnect後に候補が表示されたこと、artifact/local source一致、`404→api`の情報損失である。**高確度仮説**はinitial explicit pathが正しいVS Code session/account preferenceを確定できず、private RESTが`404`になったこと。**未確定**はwrong preferred account、session/consent例外の握りつぶし、scope/access差のいずれが実際に起きたかである。authenticated gh CLI/API成功はVS Code extension sessionのaccount/scopeを証明しない。
  - context selection root cause（確定）: original commandは`reviewRange.selectContext`（`vscode-current-context-runtime.ts:20-22,123-145`）である。handlerは`CurrentContextRuntimeComposition.selectContext`へ入り、最初に`enumerateCandidates`だけを呼ぶ（`current-context-runtime-composition.ts:72-83`）。T305の`enumerateContexts`はlocal branch/workspace候補を列挙後に、存在する場合だけT405の`augmentCurrentContextCandidates`を呼ぶ（`t305-extension.ts:420-425`）。後者はpersisted PR contextsだけを読む（`t405-review-contexts-runtime.ts:502-521`）ので、保存済みPR candidateが0ならremote detection、VS Code session取得、redetect/reconnectは起動しない。従ってGitHub remoteであってもbranch-only Current Context Quick Pickになる。
  - composition order: T305は`reviewContextsRuntimeRef`を作り、Current Context composition/runtimeを先に登録し（`t305-extension.ts:420-495,635-680`）、T405 runtimeを後から同refへ格納する（`:685-710`）。通常のT405 redetectは`options.refreshCurrentContext()`を呼ぶ（`t405-review-contexts-runtime.ts:1164`）ため、Current Context選択から既存commandを直接再入するとrefresh/cancellation循環を作る。user selection前だけに使う、Current Context refreshを呼ばないT405 preparation methodならこの循環を避けられる。
  - prompt/selection state: `VscodeCurrentPullRequestSelectionStore`はrepository+immutable HEADごとにPR contextIdまたは`false`のbranch/no-PR sentinelを保存する（`vscode-review-contexts-runtime.ts:69-137`）。既存saved PRは初回接続を不要にするauthorityである。`false`は「confirmed zero PR」には有効だが、cancel/API failureも現行redetectが同じ`selectBranch`へ畳むため、auth failureを永続no-PRとして扱う証拠にはならない。prompt loop防止は、まず1 user command内のprepare/reselectを各1回に制限し、backgroundでは一切prepareしないことが最小である。cancel/API failure後の次回explicit selectionを抑止する永続stateは、confirmed no-PRと区別できるsafe outcomeを導入するまで追加しない。manual redetect/reconnectは常に明示的な回復入口として残す。

## 結果

- 結果:
  - 推奨UX contract: 初回のuser-explicit `Current Contextを選択`でconnect/redetectを先に行い、その候補からCurrent Context Quick Pickを出す。既存`PRを再検出`も同じshared detection contractを使う。通常session取得後にtokenあり`404/api`なら`clearSessionPreference:true`を伴うaccount reselectを表示し、同一operationで1回だけPR search retryとする。成功してpreferenceが確定した後の同じ操作はreselect promptなし、全background callerは現在どおり`createIfNone:false`でpromptなし、manual `GitHub再接続` commandは後方互換で維持する。
  - redetect-onlyのreselect/retryはwrong account回復には必要だが、original user operationである`reviewRange.selectContext`からT405 detectionが呼ばれないため単独では不十分である。実装順はA（selection入口）を先、B（authenticated `404`回復）を後とする。
  - 代替案（0.5h以内）: redetectのretryを`forceNewSession:true`にする。再認証は誘発できるが、typing上account preferenceをclearして選ばせる契約ではないため、multi-accountの正しいaccount選択を保証できず推奨しない。
  - A: 初回Current Context選択→connect/redetect（各0.5h以内）: `CurrentContextRuntimeCompositionPort`へoptional `prepareExplicitSelection(signal, feedbackContext)`を追加し、`selectContext`のcandidate enumeration前に1回だけawaitする。T305は同portから`reviewContextsRuntimeRef.current?.preparePullRequestCandidateForExplicitContextSelection(...)`を呼び、T405は既存redetect logicを「refreshCurrentContextを呼ばないshared detection operation」として抽出する。saved PRが対象HEADにあればskip、未選択・candidate 0ならcreate session→search→PR候補保存→enumerationを再開する。変更候補は`src/ui/current-context/current-context-runtime-composition.ts`、`src/t305-extension.ts`、`src/t405-review-contexts-runtime.ts`、既存runtime unit fixtureである。これはT305→T405の片方向callで、T405→Current Context refreshを行わないため循環しない。
  - B: authenticated `404`→account reselect/retry（各0.5h以内）: Aのshared detection operationに、token presentかつsafe status `404/api`のときだけ`clearSessionPreference:true`で1回reselectし同一searchをretryする分岐を追加する。変更候補は`src/adapters/github/vscode-github-authentication-provider.ts`、`src/t405-review-contexts-runtime.ts`、`test/unit/t407-private-pr-context.test.ts`。Aを先に完了すればBはT305を変更しない。
  - runtime Red: Aは「session無しprivate API→public command `reviewRange.selectContext`→create session prompt 1→PR candidate Quick Pick」で現行red、成功後の同一HEAD selectionではconnect prompt 0、background recomputeでは0を確認する。cancelでは候補をbranch-onlyへ戻して同一operation内の再prompt 0、confirmed zero PRではbranch/no-PR sentinelを保存する。Bは「wrong/preferred session token→authenticated private `404`→account reselect 1→retry success→PR candidate」、次回reselect 0を確認する。AはCurrent Context composition unit＋T405 dedicated fixture、Bは既存`test/unit/t407-private-pr-context.test.ts`で表現可能である。
  - R2調査時は実装、テスト、CI、Host、performance、commit、pushを実施していない。修正対象は上記最大3ファイルであり、design/task/package/workflowは変更不要の見込みであった。
  - R2A実装結果: `reviewRange.selectContext`のunderlying compositionは候補列挙前にoptional preparation portを一度awaitする。T305は初期化順を保ったままT405 registered runtimeへ片方向に委譲し、T405 preparationは同一HEADの保存済みopen PRを検出した場合はsession promptを出さずにreturnする。候補未保存時だけinteractive token取得と既存PR search/persistence/selectionを共有実行し、Current Context refreshを呼ばないため循環しない。既存`PR再検出`は同じdetectionを実行後に従来どおりrefreshし、`GitHub再接続`は未変更である。baselineは`8cadc8431a59358a88902f87d582b373a5b547f6`、review対象はこのbaselineから将来のR2A technical headまでのdeltaに限定する。
