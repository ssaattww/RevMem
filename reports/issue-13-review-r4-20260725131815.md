## 検出・修正事項

### blocking: 既存workspace contextに対象file stateがないと空baselineを記録せず、後続fallback追加を失う

対象:

- `src/adapters/document-review-state/reconciled-document-review-state-session-provider.ts:257-304`
- `src/adapters/workspace-review-state/workspace-review-state-session-provider.ts:179-191`
- `src/core/review-state/review-state-service.ts:251-273`
- `test/unit/issue-13-owner-reconciliation-review.test.ts`
- `doc/design/issue-13-document-context-routing.md:216-241`

`reconcileCertainSource`は、lower ownerのcontextとGlobalの両方に対象file stateがない場合、baselineを記録せず即座にreturnする。

workspace contextはworkspace全体で共有され、`createdAt`は最初にcontextを作成した時刻のままである。各file stateには`updatedAt`だけがあり、file state固有の`createdAt`はない。

このため、次の正常系でfallback側の追加確認がGit ownerへ反映されない。

1. Git利用不能またはnon-Gitの時期に、同じworkspaceの別ファイルを開いてworkspace contextを作成する
2. 対象ファイルにはworkspace file stateがないまま、Gitが利用可能となる
3. Git ownerで対象ファイルの範囲Aを確認済みにする
4. Git ownerを開いた時点ではworkspace側に対象file stateがないため、空集合のbaselineを記録しない
5. Gitが一時的に利用不能となり、既存のworkspace contextへ対象ファイルの範囲Bを新規保存する
6. Git復旧時、Git側にはA、workspace側にはB、共通baselineはない
7. workspace contextの`createdAt`は別ファイルで作成した古い時刻であり、Git fileの更新時刻より新しくない
8. 実装はBを追加差分として適用せず、現在workspace snapshotをbaselineとして記録するだけで終了する
9. Git ownerはAのままとなり、Bは次回以降も差分にならない

lower ownerに対象file stateが存在しないことは、現在の確認済み集合が空であるという確実な状態である。上位ownerを開いた時点で空baselineを記録すれば、後続fallbackで作成されたBを`B - empty`として確実に反映できる。

現在の再現testは次の2種類だけで、この境界を固定していない。

- Git state作成後にworkspace context自体を新規作成するケース
- workspace側に対象file stateがあり、Gitへの初回移行時にbaselineを確立済みのケース

修正状況: 未修正。

必要な対応:

- 先に、別ファイルによって古いworkspace contextだけが存在し、対象file stateは存在しない再現testを追加する
- lower owner contextが存在し対象file stateがない場合、現在content hash・line count・source identityに対する空snapshotをbaselineとして記録する
- Git unavailable中に対象file stateを新規作成した後、Git復旧で追加範囲が反映されることを確認する
- 空baseline記録後の解除・再追加でも差分計算が安定することを確認する

### blocking: 初回昇格とbaseline記録が別commitで、設計の単一atomic transactionを満たさない

対象:

- `src/adapters/document-review-state/document-review-state-session-provider.ts:225-242`
- `src/adapters/document-review-state/document-review-state-session-provider.ts:624-665`
- `src/adapters/document-review-state/reconciled-document-review-state-session-provider.ts:136-144`
- `src/adapters/document-review-state/reconciled-document-review-state-session-provider.ts:229-241`
- `src/adapters/document-review-state/reconciled-document-review-state-session-provider.ts:332-360`
- `doc/design/issue-13-document-context-routing.md:232-248`

公開providerは、reconciliation wrapperの前にbase providerの`open`を呼ぶ。base providerは移行先にfile stateがない場合、lower ownerのintervalを`promoteFirstCertainSource`でcommitする。

その後、reconciliation wrapperがlower ownerを再読込し、sourceとtargetのinterval一致を確認してbaseline metadataを別のtransactionでcommitする。

したがって初回昇格は次の2commitになる。

1. 範囲だけを新ownerへcommit
2. 同じsourceのbaseline metadataをcommit

さらにGit ownerではworkspaceとexternal-fileを順番に処理し、`reconcileCertainSource`がsourceごとにcommitするため、複数sourceのdeltaとbaselineも1回のsnapshot CASには集約されない。

設計7.5は、確実なsource deltaと次baselineを計算した後、新ownerへ完全snapshot transactionを1回commitすると定めている。現在の構造はこの契約を満たさない。

1回目の範囲commit後に2回目のbaseline commitが失敗するかExtension Hostが終了すると、新ownerには範囲が存在するが共通baselineがない中間状態が残る。次回openまでにlower ownerが変更された場合、変更がlegacy・曖昧snapshotとして扱われ、追加または解除を失う可能性がある。

現在のtest repositoryは最終状態だけを確認し、commit回数、2回目commit失敗、複数sourceの途中失敗を検証していない。そのため最終CI成功はこのatomicity欠落を否定しない。

修正状況: 未修正。

必要な対応:

- base providerからowner昇格commitを分離し、reconciliation層でinterval deltaとbaselineを同じ`transaction.next.contextState`へ組み立てる
- 初回昇格でも範囲とbaselineを1回のCASで保存するtestを追加する
- commit回数を記録するtest doubleで、1回だけcommitされることを固定する
- commit失敗時に移行先へ範囲だけが残らないことを確認する
- workspaceとexternal-fileの両sourceが存在する場合、必要なdeltaとbaselineを1つのnext snapshotへ集約するか、設計をsource単位commitへ変更して部分成功時の回復規則を明示する
