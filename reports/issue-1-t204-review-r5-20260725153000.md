## 新規指摘

### 1. High / blocking — rename metadata片側欠落を正常returnし、transitionを黙って無視する

`parseZeroContextGitDiff`は`rename from`または`rename to`のどちらか一方を見つけるだけで`isRename = true`にする。T204側の`parseSections`もrename metadataが両方揃っていることを検証せず、`oldPath`または`newPath`が`undefined`のrename sectionを生成する。

その後`applyGitFileStateTransitions`は、rename sectionについて`oldPath`または`newPath`が欠けていれば単に`continue`する。このため、例えば次のmalformed diffが例外にならない。

```text
diff --git a/a.ts b/b.ts
similarity index 100%
rename from a.ts
```

結果として旧`a.ts`の確認済みstateがそのままcomplete post-transition snapshotへ残る。逆に`rename to b.ts`だけの場合は、新revisionに存在する可能性がある`b.ts`の未確認stateが生成されない。

これは「不確実な対応を確認済みにしない」というAC-10/AC-24、および関数JSDocの「malformed metadataをthrowする」というcontractに反する。

**必要な修正:**

- rename metadataは`rename from`と`rename to`の両方をexactly once要求する
- 片側欠落、duplicate rename metadata、空pathをtransition適用前に`SyntaxError`でatomic拒否する
- `rename from`のみ、`rename to`のみ、duplicate from/toの恒久testを追加する

### 2. High / blocking — new/delete statusと`/dev/null` sideの矛盾を黙殺し、incomplete snapshotを返す

追加validatorは`new file mode` sectionで`+++ /dev/null`を拒否するが、文字列完全一致だけを見ている。そのため次の入力は検証を回避する。

- `+++ /dev/null<TAB>timestamp`
- `+++ "/dev/null"`

validator側ではdecode後のpathが`/dev/null`でもdestinationとして扱う。一方authoritative parserはこれを`undefined`、つまりcontent不存在として扱う。

unchecked engineでは`new file mode`により`kind: "add"`となるが`newPath`が`undefined`なので、適用loopがそのsectionを黙って無視する。その結果、新規file stateを欠いたまま「complete snapshot」を正常returnできる。

同様に`deleted file mode`なのにold sideが`/dev/null`、またはdelete sectionの`oldPath`が欠けるcaseも、deleteを適用せず正常returnする経路がある。

**必要な修正:**

- `new file mode`はold sideが`/dev/null`、new sideが実pathであることを必須化する
- `deleted file mode`はold sideが実path、new sideが`/dev/null`であることを必須化する
- quoted path、TAB timestampをdecodeした後のcanonical valueで`/dev/null`判定する
- statusとheader sideが矛盾する全caseをatomic拒否するtestを追加する

### 3. Medium — authoritative parserとvalidatorのfile-section/path parser二重実装が既に仕様差を生んでいる

`git-file-state-transition.ts`、`git-diff-interval-mapping.ts`、`validated-git-file-state-transition.ts`で、section分割、quoted path、octal escape、file header prefix、TAB timestamp、status metadataを別々に解析している。

R4と今回の指摘はいずれも、この二重・三重実装間のcanonicalization差から発生している。wrapperで一部だけ先行検証する構造では、authoritative parserが認識する状態とvalidatorが検証する状態を完全一致させ続けることが難しい。

**推奨:**

- T203 parserの公開parsed section modelへcopy/add/delete/status metadataとcanonical pathを追加する
- T204はその単一parsed resultだけを使ってgraph validationとstate適用を行う
- `validated-git-file-state-transition.ts`の独自path parserを廃止する

### 4. Medium — malformed sectionを無視するguardが多く、complete snapshot contractとfail-fast方針が一致していない

適用loopには、transition kindでありながら必須pathがない場合に`continue`するguardが複数ある。parserが完全性を保証していない現状では、これらはdefensive guardではなくmalformed transitionのsilent ignoreになる。

公開contractは「malformed metadataでthrow」「complete post-transition snapshotを返す」と説明しているため、必須field欠落はloopで無視せず、parse/validation stageで到達不能にすべきである。
