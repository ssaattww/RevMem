## Blocking finding 1: `newFiles`由来の出力stateが強化validatorを通らない

### 問題

公開wrapperは処理前に`validateStateSnapshot(input.files)`を呼ぶだけで、`newFiles` metadata自体も、unchecked engineから返された`result.files`も再検証していない。

unchecked engineの`createUnreviewed`とrename更新経路では、次の値を許容する。

- `newFiles[path].fileId === ""`
- `newFiles[path].contentHash === ""`
- rename metadataの空`contentHash`

その後、unchecked側の弱い`validateStateSnapshot(active)`は空`fileId`や空`contentHash`を拒否しないため、R6で新設した公開contractを破るstateを正常結果として返せる。

### 例

plain additionに対して次を渡す。

```ts
newFiles: {
  "new.ts": {
    fileId: "",
    lineCount: 1,
    contentHash: ""
  }
}
```

`active[""]`へstateが追加され、keyと`fileId`は一致するためunchecked validationを通過する。公開wrapperは返却結果を検証しない。

### 影響

- complete snapshot contractが入力stateと生成stateで非対称になる
- persistence keyとして空IDが混入する
- 後続のcontext/global state repositoryやhistoryが不正identityを保持する
- R6で保証したと説明しているstate invariantがAPIの返却値では保証されない

### 推奨

- `newFiles` metadataを利用前に専用validatorで検証する
- 最終的な`result.files`へ`validateStateSnapshot`を必ず適用する
- input検証とoutput検証で同一validatorを使い、生成stateだけ別contractにしない
- empty fileId、empty contentHash、path/key collisionの回帰testを追加する

## Blocking finding 2: whitespace/EOLの「完全text証明」がdiffと結び付いていない

### 問題

rename同時変更で確認済み区間を維持する際、`oldTexts[oldPath]`と`newFiles[newPath].newText`を使ってwhitespace/EOL-onlyかを判定する。しかし、これら全文が次と一致するかは検証されていない。

- hunkのremoved/added lines
- diffのold/new line coordinate
- metadataのlineCount
- 対象oldPath/newPath

そのため、実際のdiffが意味変更を含んでいても、callerが無関係な同一文字列またはEOLだけ異なる文字列を渡せば、`documentsDifferOnlyByIgnoredEol`または`isIgnoredHunk`が変更を無視し、確認済み区間を維持できる。

### 例

実diff:

```diff
-oldValue
+newValue
```

入力証拠:

```ts
oldTexts: { "old.ts": "same\r\n" },
newFiles: {
  "new.ts": {
    fileId: "file",
    lineCount: 1,
    newText: "same\n"
  }
},
options: { ignoreWhitespaceChanges: false, ignoreEolChanges: true }
```

全文比較はEOL-onlyと判定し、hunkの実内容に関係なくreviewed intervalを維持する。

### 影響

AC-08、AC-10、AC-24の「証拠のない変更を確認済みにしない」に反する。API内部callerの取り違え、cache stale、path/revision mismatchがそのまま誤った確認済み表示になる。

### 推奨

- old/new全文からhunk該当行を再抽出し、removedLines/addedLinesと一致することを検証する
- lineCountと全文の行数contractを検証する
- 完全textのrevision/path identityをDTOに含める、またはcallerで構築済みのtrusted snapshot型を導入する
- mismatch時は保守的に変更扱い、またはatomic failureにする
- unrelated text、stale text、lineCount mismatchの回帰testを追加する

## Medium finding 1: 既存stateの`updatedAt`は非空だけで日時妥当性を確認していない

transition用`input.updatedAt`はunchecked engineで`Date.parse`検証される一方、snapshot内各fileの`updatedAt`はlengthしか見ていない。`"not-a-date"`がunchanged fileとして返る。

`updatedAt`がISO timestamp contractなら入力snapshotでも同一検証を行うべきである。少なくとも保存・hover・historyで日時として扱う境界とcontractを統一する必要がある。

## Medium finding 2: validatorとauthoritative parserの二重実装がさらに拡大している

現在、section split、quoted path decode、metadata path decode、file header path decode、rename/copy/add/delete status判定がwrapperとunchecked engineで重複している。R3〜R6で発生した不具合の多くはこの差分から生じている。

今回もwrapperはcopy source metadataを完全にはモデル化せず、unchecked parserへ二段階で委ねている。仕様追加ごとに片側だけ修正されるリスクが高い。

推奨は、T203 parserが返すcanonical section modelへstatus metadataとvalidation結果を集約し、T204 engineが同じ構造を一度だけ消費することである。
