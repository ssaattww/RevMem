## Findings

### T401-R001 — High — open PRが100件を超えると対象HEADのPRを見落とす

- Origin: introduced_by_change
- Location: `src/adapters/github/fetch-github-pull-request-adapter.ts` `findOpenByHead`
- Description: REST requestは`per_page=100`を指定するが、`Link` headerを処理せず1ページ目だけを候補化している。対象HEADに一致するopen PRが2ページ目以降にある場合、結果は`found`かつ空配列となり、resolverは`not-found` branch fallbackを返す。
- Impact: repositoryにopen PRが101件以上あるだけで、実在するcurrent-HEAD PRを「存在しない」と誤判定する。PR review contextではなくbranch contextが選ばれ、PR単位の進捗・base identity・後続metadata取得が誤った文脈で進む。
- Evidence: 実装は`per_page=100`を設定後、単一`fetch`結果のみを`response.json()`している。実装handoff自身も「Open-PR pagination is currently limited to the first 100 API results」をremaining riskとして記録しているが、これは要件上の検索完全性を破るためheldではなく必須修正である。現在のtestは1ページのfixtureのみで、101件目以降を検証していない。
- Required action: GitHub RESTのpaginationを最後のpageまで追跡し、全pageからexact HEAD一致候補を収集する。少なくとも、1ページ目に不一致100件、2ページ目に一致PRを置くintegration testを追加し、修正前失敗・修正後成功を確認する。

### T401-R002 — High — GitHub Enterprise remoteに対して認証providerを選択できない

- Origin: introduced_by_change
- Location: `src/adapters/github/vscode-github-authentication-provider.ts` constructor / `getAccessToken`
- Description: remote parserとAPI base URLは任意のGitHub Enterprise hostを受け付ける一方、認証session取得はprovider id `github`へ固定され、repository hostもprovider選択情報も受け取らない。したがってGitHub Enterprise用sessionを選択できない。
- Impact: public GitHub Enterprise repositoryでは未認証fallbackが偶然成立し得るが、private GitHub Enterprise repositoryではtokenを取得できずREST APIが失敗する。T401が明示的に扱うGitHub Enterprise remoteの認証済み検索経路が成立しない。
- Evidence: `parseGitHubRemote`は`git.example.test`等のenterprise hostを返し、`gitHubApiBaseUrl`も`https://<host>/api/v3`を生成する。しかし`VsCodeGitHubAuthenticationProvider.getAccessToken()`は常に`getSession("github", ...)`を呼び、hostまたはprovider idを引数・設定として受け取らない。testにもGitHub Enterprise認証sessionの選択ケースがない。
- Required action: repository hostに応じた認証provider/session取得を契約へ含める。GitHub.comとGitHub Enterpriseの双方について、正しいprovider/sessionが選択され、`createIfNone: false`のままtokenがadapterへ渡るtestを追加する。Enterprise認証をT401で扱わない判断なら、remote/APIのEnterprise対応表明と受入範囲を同時に縮小する必要がある。
