# Sub-agent実行レポート

## タスク

- 目的: Issue #116 の `Current Contextを更新` が PR Progress 自体の計算時間を大きく超える原因を通常経路から特定し、既存の正しさと無効化契約を維持した最小改善を設計する。
- タスク種別: 設計・調査
- 対象識別: branch `fix/issue-116-context-refresh`、base `d86f2da0cfc5d19cac14e90ffbf5c5a85fd08c9a`、current HEAD `76c8af6ab2998c16bd5cbbe32bd687f919bb58b7`。HEAD差分は親が作成した追跡文書だけであり、本担当は設計文書と本レポートだけを変更した。
- 検証能力: Node.js 24.18.0、npm 11.16.0、local Gitを実行可能。

## sub-agentを使う理由

- 理由: 親が進捗追跡と後続工程を担当する間に、指定された fresh specialist として Issue #116 だけのコード経路、呼出し回数、設計差分を独立に確定するため。

## 対象範囲

- 対象: 0.1.52-pre と現在 HEAD に共通する Current Context、Review Contexts、PR Progress、Global Understanding の更新順序、local Git inspection、保存済みcontext読込み、GitHub lifecycle、immutable PR diff・進捗取得、および同一refresh generation内の再利用契約。
- 対象: 通常の単一repository、単一visible document、単一保存済みPRで毎回通る重複I/O。100ユーザーで月1回以上という採用基準は、起動、active editor変更、明示再計算の各通常triggerにより満たす。

## 対象外

- 対象外: PR Progress計算アルゴリズム、Global集計アルゴリズム、長寿命cache、時間基準TTL、GitHub API呼出しを独立refresh間で省略する変更、上位timeout、広範な並列化、永続形式・public API・設定変更。
- 対象外: Issueログだけでは分離できない14,303 msと4,786 msの絶対内訳の断定、利用者環境ごとの時間目標、低頻度または品質上乗せだけの最適化。

## 指摘事項

- 指摘要約: Issueログの `PR進捗を計算` 36 msと`Global理解率を再計算` 32 msは、14,303 msの上位operationの末尾にある派生projectionであり、主要時間を説明しない。
- 指摘要約: Current Context候補補完は、保存済みcontextを読み、各PRのGitHub lifecycleを取得し、選択PRのexact diffを取得・runtime登録して進捗を計算する。そのCurrent Contextが受理されると、依存更新の先頭にあるReview Contextsがlocal候補列挙、保存済みcontext読込み、各PR lifecycle、選択PRを含むdiff・進捗取得をもう一度行う。最後に専用PR Progressが計算される。0.1.52-preの同等sourceにも同じ順序が存在する。
- 指摘要約: 単一rootでactive document、opened document、visible editorが同じ1文書、workspace folderが1つ、Current ContextがPRという通常fixtureでは、現行1回のCurrent Context更新が `inspectRepository` を候補列挙5回、fallback1回、依存Review Contexts側の再列挙5回の合計11回呼ぶ。originが1つなら1 inspectionは最低でもGit subprocess 6個であり、合計最低66個となる。exact PR diffも1取得につきbase/head検証とdiffの最低3 subprocessを使い、選択PRについて候補補完とReview Contextsで重複する。
- 指摘要約: probeの時間は大きく変動するため性能gateには使えないが、11 inspection相当が15.8秒だった事実は、Issueの14.3秒と同じ桁であり、重複subprocessが実環境で支配的になり得る裏付けとなる。元ログに各I/O stageの時刻がないため、報告された14.3秒の全量をこの原因へ帰属させない。

## 結果

- 結果: 既存設計16.2、19.1、Unit方針、受け入れ条件へ、次の2単位の最小設計を追記した。
- 結果: 単位AはCurrent Context refresh generation内のGit inspection共有である。同一inspection start pathの結果または処理中Promiseと、検査結果が返したcanonical root自体への後続検査だけを共有する。未検査descendantを推測せず、failure、abort、retry、次generationへ持ち越さない。
- 結果: 単位BはCurrent Context候補補完が得たlocal候補、repository context、GitHub lifecycle、選択PRのimmutable diff・進捗という準備結果を、直後のReview Contextsだけがgenerationとimmutable identityを検証して消費する設計である。独立したReview Contexts更新や次のイベントは新しく取得する。
- 結果（後記の設計補正前）: publish順はCurrent Context受理、選択PR diff runtime登録、Review Contexts Tree、PR Progress開始を維持する。cancel、stale、failure、identity不一致では準備結果をTree、cache、runtime、PR Progressへpublishしない。DecorationとGlobalの既存failure isolationも維持する。
- 結果: 実装担当の主な変更候補は `src/composition/extension.ts`、`src/composition/review-contexts/review-contexts-runtime.ts`、`src/ui/current-context/current-context-runtime-coordinator.ts`、`src/ui/review-contexts/vscode-review-contexts-runtime.ts`、必要に応じて `src/application/review-context/repository-resolution.ts` である。既存責務境界を保てるならinspection sessionと準備tokenの小さな型をapplicationまたはcomposition層へ置く。
- 結果: focused Redは `test/unit/issue-116-current-context-refresh.test.ts` に集約し、既存契約の補助確認が必要な場合だけ `test/unit/t609-repository-resolution.test.ts` と `test/unit/t305-projection-refresh.test.ts` を更新する。production compositionのactual wiringは `test/unit/t405-composition-regression.test.ts` 相当の実経路を通す。
- 結果: 最小TDD Red 1は、単一root fixtureで重複するactive/opened/visible/workspace入力を与え、同一start pathと返却済みrootのinspectionが1 generationにつき1回、次generationでは再実行されることを検証する。
- 結果: 最小TDD Red 2は、単一保存済みPRのproduction compositionで、Current候補補完から依存Review Contexts完了までのrepository context読込み、lifecycle、選択PR diff、Review Contexts用選択PR進捗が各1回であり、runtime登録後に専用PR Progressが開始され、候補とTreeが同じimmutable identityを持つことを検証する。独立したReview Contexts commandは新しい取得を1回行う。
- 結果（後記の設計補正前）: 最小TDD Red 3は、準備後かつpublish前のsupersede、およびlifecycle/diff failureでTree、cache、diff runtime、PR Progressがpublishされず、次generationが新規取得で回復することを検証する。
- 結果: `git diff --check` は成功した。Markdown focused lintはrepository側の設定と実行経路がないため `unsupported`。設計・レポート本文に設定回避目的の引用符やbacktickは追加していない。full testは設計調査の制約に従い実行していない。

## 設計補正

- 補正理由: 実装Green確認時点の再調査で、既存の候補補完は `progressFor` から `acquire` を呼び、Current Context受理前にexact diff cacheを保存し、検証済みimmutable snapshotをruntimeへ登録してから候補進捗を計算することを確認した。このcache保存はrepository、context、PR番号、base SHA、head SHAに束縛され、候補不採用後に別identityのTreeへ転用されない。runtime登録も候補進捗の計算に必要である。一律の延期・rollbackは今回の重複I/O削減に不要な取得API再設計となり、通常経路の実害に基づかないため撤回した。
- 補正後の最小契約: cancel、stale、failure、identity不一致の準備tokenはReview Contexts Treeへpublishせず、PR Progressを開始しない。取得中に完了したexact immutable cache保存とdiff runtime登録はrollbackしない。最終PR Progress開始前に、受理した選択と登録済みsnapshotの`contextId + baseSha + headSha + originalDiffId`完全一致を検証し、不一致なら計算しない。次generationと独立refreshは準備tokenを再利用せず、新しく取得する。
- 補正後の最小Red 3: 準備後かつTree publication前にsupersedeしたfixtureで、古いTreeとPR Progressが公開されないことを確認する。同時に、既に保存・登録されたexact immutable cache・runtimeのrollbackを要求しない。次generationで新しく取得したruntimeが受理選択と完全identity一致した後だけPR Progressが開始されることを確認する。
- 頻度判断: exact immutable cache・runtimeを候補不採用時に削除しないこと自体について、100ユーザーで月1回以上の誤表示・破損へ至る通常経路の証拠はない。防ぐべき通常経路の問題は重複取得とstale Tree・identity不一致PR Progressであり、補正後の契約がその範囲を直接覆う。

## リスク

- 未解決のリスクまたは後続対応: IssueログにはCurrent Context内部stageの時刻がないため、14,303 msと4,786 msの絶対内訳は不明。実装後は同一fixtureの決定的call countを必須gateとし、同一環境・同一workloadのbefore/after wall-clockをadvisory evidenceとして記録する。
- 未解決のリスクまたは後続対応: 複数保存済みPRでは、候補補完がlifecycleを読む件数とReview Contextsが進捗を必要とする件数が増える。設計は選択PRの重複だけを除き、他PRの未取得進捗をReview Contextsが各1回取得する。
- 未解決のリスクまたは後続対応: 準備tokenを具体的にどのinterfaceへ通すかは実装上の選択として保持する。ただしgeneration・immutable identity照合、独立refreshでの再取得、stale Tree非publish、identity不一致runtimeからのPR Progress非開始は受け入れ契約であり省略できない。exact immutable cache・runtimeの事前publicationはrollback対象ではない。
- 未解決のリスクまたは後続対応: Markdown lintはrepositoryにfocused/fullの構成がないため実行不能。後続の通常reviewでは `git diff --check` とrepository既定の設計整合確認を継続する。
