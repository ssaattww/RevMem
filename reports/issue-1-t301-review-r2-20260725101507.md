## 指摘事項

- 指摘要約: High 1件、Medium 5件
  - **High-1・blocking correctness / fallback** — `src/core/pr-progress/pr-diff-progress.ts:64-83,143-151`は、分子候補をhunk内のunique addition/deletion座標から作る一方、分母は独立した`file.additions + file.deletions`を無条件に信頼し、両者のside別一致を検証しない。`additions=1`・addition座標2件・2件確認では`2 / 1 = 2`となり進捗率が1を超える。`additions=2`・addition座標1件では全既知変更行を確認しても50%から進まない。`additions=0`・addition座標1件では`reviewedLineCount=1`、`totalLineCount=0`、`progress=1`という自己矛盾になる。これは重複hunk、不完全patch、集計値不整合を正常入力として受理するため、T402が必要とするpatch欠落・不完全時のfallback判断も阻害する。binary・明示除外を除くfileでは、addition/deletionそれぞれについてunique hunk座標数と統計値が完全一致することを検証し、不一致は推測せずfailureへ倒す必要がある
  - **Medium-1・blocking context / coordinate contract** — `src/core/pr-progress/pr-diff-progress.ts:9-17,41-46`の`ReviewedPullRequestDiffLines`は`fileId`と数値配列しか保持せず、`contextId`、PR base/head revision、original側diff IDを持たない。さらに永続状態の`LineInterval`はzero-based半開区間だが、この入力は実装上1以上のone-based座標を要求し、その変換規約を公開contractへ記載していない。したがってGlobalまたは旧revisionの範囲を同じ`fileId`・同じ座標へ変換するとcalculator内では現在PR状態と区別できず、T301終了条件のGlobal混入防止をAPI境界で保証できない。current pull-request context・expected revision・original diff IDを検証したsnapshot/builderを入力にするか、calculator自身が`ReviewContextState`と対象diff identityを受けてzero-based intervalを直接照合する必要がある
  - **Medium-2・blocking TDD / fixture validity** — `test/unit/pr-diff-progress.test.ts:20-36`の`file` helperは、line数・side・実座標に関係なくhunkを`oldStart=1`、`oldCount=1`、`newStart=1`、`newCount=1`で生成する。複数addition/deletionや7・8行目を扱う正常系も、実際にはheaderとbodyが矛盾した不可能なhunkである。さらに統計値とunique hunk座標数の過不足、複数hunk、重複actual座標、missing coordinate、duplicate reviewed file、invalid reviewed coordinateを検証していない。前回coverage findingは一部改善したが、現在のfixtureでは実model整合とHigh-1を検出できず、TDD終了条件を満たさない
  - **Medium-3・follow-on contract gap** — `src/core/pr-progress/pr-diff-progress.ts:19-31`のfile resultは`totalLineCount`へaddition/deletionを合算し、内訳を返さない。設計6.13.2とT304終了条件はfileごとの追加行数・削除行数を表示し一致確認することを要求している。後続UIが元の`PullRequestFileChange`を再joinしない限り結果だけでは表示できず、除外fileでは実countも0へ失われる。`additions`・`deletions`を結果へ保持するか、source changeを明示的に保持するself-contained contractが必要
  - **Medium-4・blocking standards gate** — `src/core/pr-progress/pr-diff-progress.ts:19-47,105-108`の公開interface propertyの大半と公開calculatorに、source documentation policyが求めるproperty contract、座標基準、zero denominator、除外時count、`@param`、`@returns`、validation failureの`@throws`がない。特にone-based入力と統計/hunk整合の責務が文書化されておらず、今回のintegration ambiguityを増幅している。前回指摘対象の`ReviewedPullRequestDiffLines`だけでなく、全公開DTOとfunction contractを現行repositoryの公開API水準へ揃える必要がある
  - **Medium-5・blocking evidence / stale report** — `reports/issue-1-t301-implementation-20260725094000.md:17-43`とPR本文は初回の不正実装時点のRed/Greenだけを記録し、現在も「reviewed座標の重複除去とGitHub側行数への上限制約」と説明している。修正後はhunkとの積集合へ変更され、上限制約は存在しないが、前回findingのdisposition、follow-up test-first commit、failure run、Green commit、final head `a5ec9465...`、run `30137524150`がreport化されていない。ユーザー指定のTDD・細かいpush・reports証跡として現状を再現できないため、review follow-up reportまたはimplementation report追記とPR本文更新が必要
- 前回finding disposition:
  - 前回High-1「任意座標を件数だけで算入」は、hunk実座標との積集合へ変更され、unknown/context座標を直接算入する経路は解消した
  - 前回High-2「独自簡略model」は、既存`PullRequestFileChange`入力とstatus・old/new path保持へ変更され、rename-only分類を後続へ渡せるようになった

- 追加確認でfindingなし: addition/deletionをside別に交差判定する点、replacementを2行で数える点、unknown context座標を除外する点、rename-onlyのstatus・path保持、binary/user glob理由、file input順、同一fileId重複拒否、修正headに紐づくcurrent-main merge ref CIには上記以外の問題を確認しなかった
