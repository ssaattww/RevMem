## 指摘事項

- 指摘要約: High 2件、Medium 3件、Low 2件
  - **High-1・blocking stale-diff correctness** — `src/core/pr-progress/pr-diff-progress.ts:9-16,41-46,57-64,119-146`は`reviewContext`と`expectedContext`のcontext ID・base/headを照合するが、`files: PullRequestFileChange[]`自体はbase/head identityを保持せず、`expectedContext`と同じ呼び出し元が独立に渡すだけである。したがってPR更新後に旧cacheの`files`をcurrent contextと組み合わせても検出できず、同じ`fileId`・座標が存在すれば旧diffを現在PRの進捗として算入する。また`originalDiffId`は非空だけを検証し、base/headとの関係を検証しないため、`originalReviewedByDiff`に残る旧comparison keyを指定して旧削除行を算入できる。型コメントの「exact PR comparison」を保証するには、adapterが生成する`PullRequestDiffSnapshot`等へcontext ID・base/head・original diff ID・filesを一体化し、そのsnapshot identityをcontextと照合する必要がある
  - **High-2・blocking malformed-hunk correctness** — `src/core/pr-progress/pr-diff-progress.ts:78-105`はheaderのold/new body件数とunique addition/deletion数だけを検証し、`DiffHunk.lines`が`oldStart`・`newStart`からsource orderで連続すること、context行に両side座標があること、additionにoldLineがなくdeletionにnewLineがないこと、hunk間の順序・非重複・delta整合を検証しない。例えば`oldStart=1, oldCount=0, newStart=1, newCount=1`、addition `newLine=99`、`additions=1`は全検証を通り、line 99のreview stateを100%として数える。R2の統計値過不足は解消したが、実座標がhunk headerと無関係でも受理されるため、不完全parse・adapter不具合・破損cacheを保守的に拒否できない。old/new cursorをline kindごとに進め、各座標、opposite-side absence、hunk ordering/deltaを検証する必要がある
  - **Medium-1・blocking TDD / fixture validity** — `test/unit/pr-diff-progress.test.ts:10-26,63-110`はheader/body countを自動生成するよう改善したが、line座標をhunk startから生成・検証しない。`hunk(1,1,[addition newLine=1])`は実Gitでは成立せず、先頭追加なら`-0,0 +1`、old line 1後への追加なら`-1,0 +2`である。さらに成功するaddition-only・deletion-only、valid multiple hunk、stale diff identity、wrong originalDiffId、hunk startとline座標の不一致、context座標欠落、file単位progress、zero denominator、除外理由を検証していない。特にT301終了条件の「理由を返す」は現testが`excluded`だけを確認し`exclusionReason`をassertしないため固定されていない
  - **Medium-2・blocking standards gate** — `src/core/pr-progress/pr-diff-progress.ts:9-47,119-122`の公開interface propertyの大半と公開calculatorに、source documentation policyが求めるproperty contract、zero-based/one-based変換、zero denominator、除外時count、snapshot identity、`@param`、`@returns`、validation failureの`@throws`がない。R2で追加された型もsummaryまたは一部property commentだけで、公開API文書findingは未解消である
  - **Medium-3・blocking evidence / stale report** — `reports/issue-1-t301-implementation-20260725094000.md:17-43`とPR本文は初回実装のRed/Greenと「GitHub側行数への上限制約」を記録したままで、現在の`ReviewContextState`入力、統計/hunk厳密一致、addition/deletion内訳、R2 follow-upのtest-first証跡、修正commit、最終head `5551e070...`、run `30138438036`を記録していない。R2 report追加後の4 commitはsource/test/indexだけで、implementationまたはfollow-up report更新がない。現実装と再現証跡を一致させ、PR本文も更新する必要がある
  - **Low-1・non-blocking held numeric boundary** — `file.additions`と`file.deletions`は個別にsafe integerを検証するが、`:147-153`のfile合計とaggregate合計がsafe integerかを検証しない。実GitHubの通常規模では到達しないためnormal path blockerにはしないが、pure API contractとしては合計overflowを拒否するか上限を定義する余地がある
  - **Low-2・non-blocking held performance/robustness** — `:66-75`はreviewed intervalを1行ずつSetへ展開するため、変更行が少なくても巨大intervalや破損した永続stateでExtension Hostを長時間占有し得る。T607の性能最適化およびT603/T606の破損入力対策と重なるため本taskではheldとするが、changed coordinate側をinterval検索する実装なら展開を避けられる
- R2 finding disposition:
  - R2 High-1「統計値とhunk座標数の不一致」はaddition/deletion side別に厳密一致させ、duplicate actual coordinateも拒否するためclose可能
  - R2 Medium-1「PR/Global/revision境界」は`ReviewContextState`を直接受け、kind、context ID、base/head、file revisionを検証するよう改善した。ただしdiff filesとidentityが一体化されず、originalDiffIdもbase/headへ結び付かないためpartial closeに留まる
