### blocking: 初回昇格sourceを二度読みし、未反映の変更をbaselineだけで消費する

対象:

- `src/adapters/document-review-state/document-review-state-session-provider.ts:218-242`
- `src/adapters/document-review-state/document-review-state-session-provider.ts:614-657`
- `src/adapters/document-review-state/reconciled-document-review-state-session-provider.ts:193-218`
- `src/adapters/document-review-state/reconciled-document-review-state-session-provider.ts:245-263`

現在の処理は、初回昇格時に同じlower ownerを二度読みする。

1. base providerがworkspaceまたはexternal-file sourceを読み、最初の確実なsourceからpromotion transactionを作る
2. capturing repositoryがそのtransactionをメモリへ保持する
3. reconciled providerが`loadLowerOwnerSources`でworkspaceとexternal-fileを再度読み込む
4. 1回目のsourceを反映済みの`targetSession`をplanned stateの初期値とし、2回目のsource snapshotをbaselineへ保存する

sourceはread-onlyではあるが、二つの読込の間に別windowまたは並行commandがlower ownerを更新できる。cross-window lockが未接続であることを考慮しなくても、複数のasync commandが同じExtension Host内で進行する可能性がある。

再現可能な経路:

1. 1回目のworkspace readは範囲Aを返す
2. captured promotionはtargetへAを追加する
3. 2回目のworkspace readまでにsourceが範囲Bへ変更される
4. planned targetは既にAであり、source Bとの初回比較ではsource contextの`createdAt`がtarget更新より古いため、Bを追加またはAを解除しない
5. baselineだけをBへ進め、targetはAのままcommitする
6. 次回openではsource Bとbaseline Bが一致するためdeltaは0となり、Bへの変更は以後自動反映されない

設計7.1は全sourceをread-onlyで読み込んでからnext snapshotを計算する契約であり、7.8は初回昇格範囲と次baselineを同じsource情報から1回のCASへ集約することを要求している。現在はcommit回数は1回でも、promotion rangeとbaselineの観測snapshotが一致していない。

修正状況: 未修正。

必要な対応:

- 初回promotionのために読んだsource snapshotをそのままreconciliation planningへ渡し、同じownerを再読込しない
- またはcaptured promotionの`expected`をplanned stateの開始点とし、2回目に一括取得した全sourceだけからrangeとbaselineを再計算する
- 1回目にA、2回目にBを返すmutable source fixtureを追加し、targetとbaselineが同じsource snapshotを表すことを固定する
- source変更をbaselineだけで消費しないことを確認する

### blocking: 複数sourceの相反deltaでlower-priority external-fileがworkspaceを上書きする

対象:

- `doc/design/document-context-routing.md:28-36`
- `doc/design/document-context-routing.md:333-345`
- `src/adapters/document-review-state/reconciled-document-review-state-session-provider.ts:320-342`
- `src/adapters/document-review-state/reconciled-document-review-state-session-provider.ts:379-446`

owner優先順位は`workspace > external-file`である。一方、Git ownerへreconcileするときはworkspaceを先、external-fileを後にplanned snapshotへ適用する。各sourceのremovalは直前sourceを適用済みのtargetから直接減算されるため、後から処理されるexternal-fileのremovalがworkspaceの現在状態を上書きできる。

再現可能な経路:

1. Git、workspace、external-fileのbaselineが範囲Aを持つ
2. Git unavailable中、external-file側でAを解除する
3. その後workspace側でAを再確認し、範囲Bも追加する。workspaceの現在状態はA+Bとなる
4. Git復旧時、workspace deltaでBを追加し、planned targetはA+Bとなる
5. external-file deltaが後からAを解除し、最終targetはBだけになる

`OwnerSourceSnapshot`は`sourceUpdatedAt`を保持するが、相反deltaの優先順位判定には使用していない。固定順のため、より新しいworkspace操作またはowner優先順位を考慮できない。

これは同じfileをworkspace windowとworkspaceなしwindowで扱う本Issueの通常経路で発生し得る。複数sourceを1回のCASへまとめること自体は満たしているが、集約結果がユーザーの最後の確認操作またはowner優先順位を保存しない。

修正状況: 未修正。

必要な対応:

- 同一rangeに対する相反deltaの競合規則を設計へ追加する
- 少なくとも`workspace > external-file`を結果へ反映するなら、lower-priority sourceがhigher-priority sourceの現在reviewed rangeを解除しないようにする
- 時系列を採用する場合はrange単位の由来または更新情報が必要であり、context/file全体の`updatedAt`だけで安全に決められる範囲を明示する
- workspace追加とexternal解除、workspace解除とexternal追加の両方向をtestする

### non-blocking: `ownerReconciliation`が正式なpersisted core contractに存在しない

対象:

- `src/adapters/document-review-state/reconciled-document-review-state-session-provider.ts:37-50`
- `src/core/contracts/review-state.ts:162-187`
- `src/adapters/state-repository/file-system-review-state-repository.ts:95-149`

`ownerReconciliation`はadapter内の`ReconciledReviewContextState`だけに追加されている。永続化documentの正式型である`ReviewContextState`にはfieldがなく、schema version 1のdecoder・validatorもsnapshotの構造を検証せず、未知のobjectを`ReviewStateCommit`へcastしている。

現在のJSON clone、object spread、serializerは未知fieldを偶然保持するため正常データのround-tripは成立する。しかし次の問題が残る。

- core/application層はpersisted baseline contractを型として参照できない
- malformed baselineをload時に拒否できず、adapter内で`baseline.sourceOwner`等へアクセスした時点で失敗する
- schema migrationまたは将来のstate再構築でfield保持がcompile-timeに保証されない
- contract typecheckがbaseline欠落を検出できない

対応案:

- source snapshot型と`ownerReconciliation`をcore persisted contractへ移す
- persistence readerでowner、IDs、hash、line count、timestamps、intervalを検証する
- filesystem repositoryを使ったrestart round-tripとmalformed baseline rejectionを追加する
- additive optional fieldとしてschema versionを維持する場合も、その互換性方針を設計へ明記する

### non-blocking: writable session openでowner解決とGit inspectionを重複実行する

対象:

- `src/adapters/document-review-state/persisted-document-review-state-session-provider.ts:30-46`
- `src/adapters/document-review-state/document-review-state-session-provider.ts:216-282`
- `src/adapters/local-git/local-git-adapter.ts:108-160`
- `src/ui/normal-editor/review-command-registration.ts:54-83`

public providerの`open`はreconciliation済みsessionを取得した直後、同じdescriptorを`loadForDecoration`へ渡してactive ownerを再解決する。`loadForDecoration`はLocal Git inspectionを再実行する。

remoteを持つ通常repositoryでは1回のinspectionで次の6processを起動する。

- `git --version`
- `git rev-parse --show-toplevel`
- `git remote`
- `git remote get-url`
- `git symbolic-ref --quiet HEAD`
- `git rev-parse --verify HEAD^{commit}`

したがってcommand session openだけで最大12processとなる。command適用後はvisible decoration refreshが実行され、さらに同じdocumentのowner inspectionが走るため、単一の確認操作で最大18processとなり得る。

reconciliation providerは実CAS成功後のplanned snapshotを既に返しているため、通常経路の再読込は冗長である。また、二度目のowner解決中にHEADまたはGit availabilityが変化すると、最初のsessionと再読込結果が異なるraceも増える。

対応案:

- successful CASが返したplanned snapshotをpublic sessionとしてそのまま利用する
- durable reloadが必要なら、解決済みrepository targetを使って直接reloadし、Git inspectionを繰り返さない
- Git inspection結果をdocument/HEAD単位で短時間cacheし、明示的なrepository change eventで無効化する
- command 1回あたりのinspector invocation回数をtestで固定する

### held: `objectExists`が任意のexit code 128をmissing objectとして扱う

対象:

- `src/adapters/local-git/local-git-adapter.ts:79-80`
- `src/adapters/local-git/local-git-adapter.ts:194-214`

`HEAD^{commit}`については既知unborn診断だけを受理するよう修正された。一方、`git cat-file -e`を使う`objectExists`はexit code 1または128をstderr分類なしで`false`へ変換する。破損object database、権限、I/O failure等の128もmissing objectとして隠蔽し得る。

このmethodはrevision mapping側の依存であり、今回のdocument routing正常経路では使用しない。またbehavior自体はPR baseから存在するため、本PRのblockingにはしない。T203以降のmapping接続前に、既知missing-object診断と予期しないfailureを分離する必要がある。
