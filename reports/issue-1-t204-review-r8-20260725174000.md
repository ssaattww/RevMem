## Blocking findings

### 1. 過去のpathへ戻る正当なrenameが失敗する

`previousPaths`にrename先が既に含まれる状態で、そのpathへ戻るrenameを適用すると、実装はrename先を`previousPaths`から除去しない。

例:

- currentPath: `b.ts`
- previousPaths: [`a.ts`]
- rename: `b.ts` → `a.ts`

生成stateは次の形になる。

- currentPath: `a.ts`
- previousPaths: [`a.ts`, `b.ts`]

返却後の強化validatorは`previousPaths`が`currentPath`を含むため例外にする。通常のrename履歴として正当な「元の名前へ戻す」操作を処理できない。

修正では、rename先を履歴から除去した上で旧pathを重複なしで追加する必要がある。rename chain、swap、A→B→Aの回帰testが必要。

### 2. 同じsourceへのdeleteとrenameで返却結果が自己矛盾する

同一old pathをdelete sectionとrename sectionの両方が参照するmalformed diffをcross-sectionで拒否していない。

現在の処理順では:

1. delete planningでsource IDを`plannedDeletes`へ追加
2. rename planningでも同じsource IDを`plannedRenames`へ追加
3. activeから一度削除
4. rename処理で同じIDをdestinationへ復元
5. `deletedFileIds`には同じIDを残したままreturn

結果として、`files`には存在するのに`deletedFileIds`にも含まれる矛盾したsnapshotになる。返却state validatorは`files`だけを検証するため検出できない。

source operation graphを事前検証し、少なくともdeleteとrenameの同一source併存、同一sourceの重複deleteをatomicに拒否する必要がある。結果全体について`deletedFileIds`と`files`の排他性も検証すべき。

## Medium findings

### 3. new destination追加処理が二乗時間になる

`addDestination`ごとに`newDestinations.values()`を全走査し、最終追加時にも`Object.values(active)`を全走査している。大量のaddition/copy/ambiguous renameではO(n²)になる。

file ID setとactive path mapを維持すればO(n)で処理できる。

### 4. parser／validatorの二重実装が継続している

quoted path、file header、section split、status metadataをvalidated wrapperとunchecked engineの双方で解析している。過去R4〜R7で実際に仕様差による不具合が繰り返されているため、共通のauthoritative parsed section modelへ統合すべき。
