## 5. Finding dispositions

### T603-R006 — medium — addressed

#### Source defect

`NodeNonGitSnapshotStorage.get()` quarantined malformed/invalid-base64 snapshot entries directly. The only logic that invalidated matching latest pointers lived in `quarantine(snapshotId)`, so direct reads and startup migration could leave a valid authoritative pointer naming a removed snapshot.

#### Fix

`get(snapshotId)` now delegates non-future corruption to `this.quarantine(snapshotId)` instead of quarantining only the wrapper path. The existing `quarantine()` boundary preserves the corrupt wrapper and invalidates every valid latest pointer naming that snapshot ID.

Unsupported future schema still throws and is not treated as ordinary corruption.

#### Regression coverage

- direct malformed/current-schema wrapper + valid latest pointer;
- startup metadata migration with malformed wrapper + valid latest pointer;
- existing gzip/hash/envelope corruption and latest invalidation regressions remain active.

### T603-R013 — medium — addressed

#### Source defects

1. Existing history lines were checked for duplicate IDs among themselves, but the newly appended event was not compared against that set.
2. `migratePersistedReviewHistoryFile()` had no expected repository-owner input, and startup migration discarded owner identity before scanning history.

#### Fix

`prepareExistingHistory()` now returns its validated `eventIds`. Before appending to a valid history file, `append()` rejects a new event whose ID is already present. This rejection preserves the valid active history and does not quarantine it as corruption.

The history preparation boundary now accepts an `expectedRepositoryId`. Existing records are required to belong to that repository while still allowing multiple `contextId` values for the same repository/month.

Startup migration now retains owner identity per persistence root:

- a valid workspace state contributes its repository ID;
- a valid repository/external-file manifest contributes its repository ID;
- the owner is supplied to each monthly history migration under that root;
- roots with absent/uncertain owner state are still scanned for snapshots/history, but owner-specific history validation is only applied when the owner identity was validated.

#### Regression coverage

- existing-vs-new `eventId` collision rejects without changing/quarantining the valid file;
- direct startup-history migration boundary resets a wrong-owner history when expected owner is supplied;
- repository startup wrong-owner isolation remains covered;
- same-repository multiple contexts remain explicitly legal.

### T603-R015 — medium — addressed

#### Source defect

R001's `uncertainStorageRoots` correctly hid stale owner-wide reviewed state after corruption, but it was only cleared by `save`/`commit`/`create`. A later successful read-only `load()` could not restore state because the coherent repository's dynamic `getCurrent()` returned through the still-sticky root guard.

#### Fix

`prepareTarget()` now resolves the storage route before preparation. When complete persistence preparation returns a certain state, it clears both:

- target-level uncertainty; and
- owner-root uncertainty.

If preparation is uncertain or throws, the root remains fail-closed. Thus no stale cached state becomes visible before the persistence set has successfully passed the preparation/validation boundary.

#### Regression coverage

The regression performs valid save → downstream persisted corruption → failed/hidden load → persisted repair → read-only reload → `getCurrent()` restoration in the same repository instance.
