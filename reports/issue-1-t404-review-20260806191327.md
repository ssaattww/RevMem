## Findings

### T404-R001 — blocking — 既存Review State repositoryとは別のsource of truthを追加している

- Origin: introduced_by_change
- Location:
  - `src/application/github-pr-context/github-pull-request-context-layer-store.ts:1-5`
  - `src/adapters/github/node-github-pull-request-context-layer-store.ts:11-33`
  - direct dependencies: `src/core/contracts/review-state.ts`, `src/adapters/state-repository/*`
- Description:
  - T404は`GitHubPullRequestContextLayer`と`github-pr-context-layers.v1.json`を新設し、既存の`ReviewContextState(kind: "pull-request")`、`FileReviewState`、`RepositoryGlobalState`、T104のmanifest-last repositoryを使用していない。
  - 保存先も設計の`globalStorageUri/repositories/<repository-id-hash>/...`ではなく、global storage root直下の単一JSONである。
  - 新modelはstable file ID、previous paths、original-side reviewed ranges、content hash、line count、context/Global atomicity、history connectionを保持しない。
- Impact:
  - 既存command、decoration、PR progress、Global mapping、historyが参照する状態とT404の状態が分離する。
  - T303で保存するoriginal-side削除行やT501のGlobal状態をlosslessに復元できない。
  - repositoryを跨いだ1件の破損entryが全repositoryのPR layer loadを阻害する。
  - T405は既存状態と新状態のどちらを正とするか決められず、変換または二重更新が必要になる。
  - このままではAC-11 / AC-21 coreを製品状態基盤上で満たさない。
- Evidence:
  - T104はPR/Git状態をrepository hash配下のmanifest/context/Global snapshotとして保存し、complete snapshot CASを提供している。
  - T404 changed filesにはT104 repositoryを利用または拡張するコードがない。
- Required action:
  - PR layerを既存`ReviewContextState`および`FileReviewState`で表し、T104の`resolveReviewStateStorageRoute`と`FileSystemReviewStateRepository`を唯一の永続化基盤として使用する。
  - 複数PRのlist/select用metadataが必要なら既存manifest/contextから導出し、別のauthoritative range storeを作らない。
  - contextとGlobal、original-side state、history契約を保持した統合testを追加する。

### T404-R002 — high — 同一processの並行更新で別PR layerを失う

- Origin: introduced_by_change
- Location: `src/adapters/github/node-github-pull-request-context-layer-store.ts:25-33`
- Description:
  - `upsert`と`remove`は`#read()`後に完全documentを`#write()`するread-modify-writeだが、同一storage pathに対するserialization、expected version、CASがない。
  - 2つの`upsert`が同時に空documentを読み、各々1 layerを書いた場合、最後のrenameだけが残る。
  - `remove`と`upsert`、同一PRのrevision更新同士でも同じlost updateが発生する。
- Impact:
  - 別PRを分離して保存するT404の主要要件を通常の非同期処理だけで破る。
  - 複数window/process排他を扱うT604以前に、単一Extension Host内で状態消失が発生する。
- Evidence:
  - T104-2は同一instance・storage root単位のsave/commit直列化を既に実装している。
  - T404 storeにはwrite queueもCASもない。
- Required action:
  - T104 repositoryを再利用するか、少なくとも同一storage ownerの操作を直列化し、stale expected snapshotを拒否する。
  - `Promise.all`による別PR upsert、同一PR update、remove/update interleavingの再現testを先に追加する。

### T404-R004 — high — 同じGitHub PRがcaseまたはdefault port差で別context IDになる

- Origin: introduced_by_change
- Location: `src/application/github-pr-context/github-pull-request-context-layer-store.ts:7-20`
- Description:
  - `normalizeIdentity`はhostだけをlowercaseし、owner/repositoryのcaseを保持する。
  - `AUTHORITY`は`github.com:443`を許し、`github.com`と別IDにする。またportの有効範囲やcanonical default portを検証しない。
  - T202/T401のcanonical identityはGitHub.comのowner/repositoryをlowercaseし、default portを除去する。
- Impact:
  - remote由来の`ssaattww/revmem`とGitHub metadata由来の`ssaattww/RevMem`が別contextとして保存される。
  - `github.com`と`github.com:443`でも同じPRの状態が分裂する。
  - commit追加後の状態継続、別PR分離、cache identityが不安定になる。
- Required action:
  - `parseGitHubRemote` / `canonicalGitHubAuthority` / T202 canonical remote policyを共有し、canonical `GitHubRepositoryIdentity`だけをcontext ID生成へ渡す。
  - GitHub.com case差、Enterprise case policy、default/non-default port、invalid portを固定するtestを追加する。

### T404-R005 — high — 独自path/range modelが既存canonical filesystem contractと状態表現を破る

- Origin: introduced_by_change
- Location: `src/application/github-pr-context/github-pull-request-context-layer-store.ts:1-5,22`
- Description:
  - `files`をpath文字列からinterval配列へのplain objectとして再定義し、stable file ID、filesystem semantics、original-side state、content hash、line countを失っている。
  - `normalizeFiles`は全backslashを拒否するためPOSIX上の有効な`a\b.ts`を保存できない。
  - 一方でNUL、control characters、不正UTF-16 surrogate、Windows reserved device name、trailing dot/spaceを検証せず、Remote Windowsのcanonical path契約を満たさない。
  - intervalはoverlapを拒否するだけで、設計が要求するsort・重複/隣接結合済みcanonical rangeへ正規化しない。
  - plain objectへ任意pathを代入するため、`__proto__`のような有効なfile nameをown entryとして安全に保持できない。
- Impact:
  - OS/remote環境により有効fileが保存不能、または非canonical pathを別fileとして誤認する。
  - rename追従、original-side削除行、確実性検証に必要なmetadataを失う。
  - noncanonical intervalが後続の表示・進捗・migrationで別解釈される。
- Required action:
  - core `LineInterval`と既存normalizer、stable `fileId`、`FileReviewState`を再利用する。
  - pathは明示的な`FileSystemPathSemantics`と共通canonical validatorを通す。
  - pathをkeyにする必要がある補助indexでは`Map`またはprototypeを持たないobjectを使用し、special keyをtestする。

### T404-R007 — high — atomic publicationがflush要件を満たさず、成功後のdurabilityを保証しない

- Origin: introduced_by_change
- Location: `src/adapters/github/node-github-pull-request-context-layer-store.ts:33`
- Description:
  - `writeFile`後にfile handleの`sync()`を行わず、そのまま`rename`している。
  - design 15.2とT104のatomic storeはtemp write、file flush、close、replaceを要求・実装している。
  - temp nameも`process.pid + Date.now()`だけで、同一millisecondの並行writeで衝突し得る。
- Impact:
  - APIが成功を返した直後のprocess/host failureで、保存済みと通知したreview stateが失われる可能性がある。
  - concurrent writeでは`EEXIST`またはcleanup競合が発生する。
- Required action:
  - T104の`NodeAtomicTextFileStore`とrepository commit pathを再利用する。
  - 独自実装を残す場合はunique temp、file sync、close、replace、best-effort cleanup、failure injection testを実装する。
