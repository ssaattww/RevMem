## 指摘事項

### High / blocking — `+++` headerのTAB suffixによりduplicate destination validationを回避できる

`validated-git-file-state-transition.ts`のnew-file destination抽出は、`+++ `以降を`decodeMetadataPath`へそのまま渡し、先頭の`b/`だけを除去している。この処理はTAB以降のtimestamp等を除去しない。

一方、既存のauthoritative parserである`parseZeroContextGitDiff`の`decodePath`は、非quoted pathについてTABより前だけをpathとして採用する。したがって、同一diffに次のようなsectionがある場合、validatorと本体でdestination identityが一致しない。

```diff
diff --git a/source.ts b/dest.ts
copy from source.ts
copy to dest.ts
diff --git a/dest.ts b/dest.ts
new file mode 100644
--- /dev/null
+++ b/dest.ts	2026-07-25 15:00:00 +0900
@@ -0,0 +1 @@
+new
```

validatorはdestinationをそれぞれ`dest.ts`と`dest.ts\t2026-...`として扱うため、重複を検出しない。その後、authoritative parserはaddition destinationを`dest.ts`へ正規化するため、R3で防止対象とした同一destination transitionが本体へ到達する。

この差異は、validatorがauthoritative parserと別のpath decoder・section parserを実装したことに起因する。既存parserが明示的に受理・正規化する入力であるため、単なる不正diff扱いにはできない。

必要な修正:

1. new-file `+++` pathをauthoritative parserと同一規則でcanonicalizeする
2. 可能ならraw diffの再解析を避け、`parseZeroContextGitDiff`の結果または共有path decoderからdestinationを取得する
3. TAB suffix付きnew-file headerとcopyが同一destinationを指す回帰testをtest-firstで追加する
4. quoted path、space、UTF-8、TAB suffixでvalidatorとauthoritative parserのpath identityが一致するtestを追加する
