## 指摘事項

### T604-R001 — High — lease ownershipのread-then-mutate raceがsuccessor lockを更新・削除できる

- origin: `introduced_by_change`
- location: `src/adapters/state-repository/storage-root-lock.ts:106-110,115-136,150-180`
- description: stale recoveryはlock内容をreadした後にpathをrenameし、内容不一致なら元pathへrenameし戻す。releaseはowner tokenをread確認した後にpathを`rm`し、renewもtokenをread確認した後に同じpathを`r+`でtruncateする。各確認とmutationはatomicではないため、その間にexpired ownerが回収されsuccessorが`lock`を作成すると、旧ownerのreleaseがsuccessorを削除し、renewがsuccessorを旧tokenへ書き換え得る。recoveryのrestoreもPOSIXではsuccessorを置換し得て、Windowsではrestore失敗を握りつぶしてrecovery fileを残す。さらにrenew failureは`failure`通知だけでoperationを継続するため、leaseを失ったwriterがsuccessorと並行してpublishできる。`expiresAt < now`はexact-expiryをlive扱いし、wall clock rollbackはbounded timeoutを延ばす。
- impact: live lock非奪取、owner-checked release、deterministic stale recovery、cross-process CAS / history exclusionというT604の中心contractが破れ、mixed / lost state、history lost update、cleanup競合を起こせる。
- evidence: owner token確認後の`rm` / `open("r+")`にinodeまたはgeneration fencingがなく、operation前後に所有権再確認もない。focused testはこのinterleaving、renew failure、exact expiry、clock rollbackを作らない。
- required action: stale recovery、renew、releaseの全mutationをsuccessorへ作用しないownership-conditional protocolへ変更し、lease lostをwriterへ伝播して以降のpublicationを禁止する。monotonic elapsed timeoutとexact-expiry contractを定義し、release-vs-reacquire、renew-vs-recovery、複数recoverer、renew failure、clock境界のdeterministic multi-process Red / Greenを追加する。

### T604-R002 — High — acquire途中終了がexpiryのないcorrupt lockを残し回復不能にする

- origin: `introduced_by_change`
- location: `src/adapters/state-repository/storage-root-lock.ts:45-58,93-147`
- description: acquireは`open("wx")`でpathを可視化した後、そのfileへ直接JSONを書きflushする。process crash、write / sync / close failureではzero-byte / truncated / malformed lockが残り得る。`parseLock`失敗はstale候補にもowner-owned cleanupにもならないため、全後続callerがbounded timeoutを繰り返すだけで自動回復しない。write失敗したacquirer自身も作成済みpathを除去しない。
- impact: Issue #72のcrash / partial lock recoveryを満たさず、1回の容量不足・途中終了で当該storage rootのstate、history、cache、snapshot writeを恒久停止できる。

- required action: lock publication自体をcrash-resilientにし、作成途中failureをownerが安全にcleanupする。zero / truncated / malformed / future-invalid lockの回復policyを、live writerを奪わない外部evidenceとbounded expiryで定義し、process killおよびwrite / sync / close failure fixtureでrootが再利用可能になることを固定する。
