## Findings

### T403-R001 — mixed remote failureでgeneric API failureを含んでもoffline cacheへfallbackする

- Severity: high
- Origin: introduced_by_change
- Location: `src/application/github-pr-cache/github-pull-request-cache-service.ts` `allowsOfflineFallback`
- Description:
  - 現在の判定はremote attempt配列のうち一件でも`rate-limit`または`network`ならtrueになる。
  - そのため、例えば`github-patch=rate-limit`かつ`github-content=api`、または`github-patch=api`かつ`github-content=network`のようにgeneric API failureを含むmixed resultでもcacheを返す。
  - testは全remote attemptが同一理由のケースと、全remote attemptが`api`のケースしかなく、mixed caseを検証していない。
- Impact:
  - 「429またはnetwork failure時に限る」「generic API failureではcacheを代用しない」というT403 contractを満たさない。
  - authentication、permission、repository state、response validation等のgeneric API failureを古いcacheで隠し、利用者へ取得成功相当のoffline resultを返す可能性がある。
- Evidence:
  - `allowsOfflineFallback`は`attempts.some(...)`であり、他のremote attemptのreasonを検査しない。
  - `non-offline API failures do not substitute cached data` testは`github-patch`と`github-content`の両方を`api`に固定している。
- Required action:
  - remote acquisition全体のterminal reasonがoffline許可理由だけで構成される場合に限定する、またはT402のterminal failure reasonを単一の明示contractとしてT403へ渡す。
  - `rate-limit + api`、`network + api`、順序を入れ替えたmixed attemptの回帰testを先に追加し、cacheを返さないことを確認する。
