## Findings

### R65-001 — HIGH — Output diagnostics can disclose private repository data through raw error messages

- Origin: `introduced_by_change`
- Location: `src/application/operation-feedback/operation-feedback.ts` (`failureDetails`, `recordFailure`), with callers in `src/t405-review-contexts-runtime.ts` and Review Contexts/normal-editor operation wrappers.
- Description: the new diagnostic boundary copies `Error.name` and `Error.message` directly into `OperationLogEntry`, and `formatOperationLogEntry` only normalizes line breaks. There is no central redaction or safe diagnostic projection.
- Impact: rev5 explicitly forbids repository paths, PR titles, credentials/tokens and source text in `Output > Review Range`, but caught dependency errors are not constrained to safe messages. For example, filesystem persistence rethrows Node filesystem errors containing absolute paths, and `GitCommandFailedError` includes Git invocation arguments in its message. Those errors can now flow directly into the Output channel. In a private-repository scenario this violates the security/privacy contract introduced by this PR.
- Evidence:
  - design rev5 §16.10/§18 prohibits repository path, private PR title, credentials/tokens, source text and stack trace in diagnostics;
  - `failureDetails()` returns `{ errorName: error.name, message: error.message }` unchanged;
  - `recordFailure()` appends that data directly to the host;
  - `NodeAtomicTextFileStore` propagates raw non-ENOENT filesystem errors;
  - `GitCommandFailedError` formats `invocation.argumentsList` into `error.message`;
  - new tests assert line normalization and raw message preservation but do not test redaction.
- Required action: make the operation-feedback boundary safe by construction. Introduce a central sanitization/typed-diagnostic projection that removes or replaces paths, repository/PR identity, credential/token material and source-bearing details before `appendLog`. Add regression tests using representative `GitCommandFailedError`, filesystem errors with absolute private paths, URL/token-like content, PR-title-like content, and multiline messages.

### R65-002 — HIGH — `NodeGitCommandExecutor` no longer guarantees a bounded timeout lifecycle

- Origin: `introduced_by_change`
- Location: `src/adapters/local-git/node-git-command-executor.ts`, timeout/termination path.
- Description: after `timeoutMs`, the executor sends SIGTERM and schedules SIGKILL after one second, but it still settles only from `close` or `error`. It does not check `child.kill()` return values, does not start a post-SIGKILL bounded-failure timer, does not destroy/unref streams when `close` never arrives, and treats a post-timeout `error` event as a raw process error rather than preserving the timeout `GitCommandFailedError` contract.
- Impact: a subprocess that ignores termination, cannot be signalled, or otherwise never produces `close` can leave the Promise pending indefinitely despite the configured timeout. That can leave review operations and the activity Status Bar stuck and violates the rev5 process-failure contract.
- Evidence:
  - rev5 §9.5 explicitly requires SIGTERM, diagnostic capture for signal-send failure, escalation to SIGKILL, a second grace period, and a bounded failure that destroys streams/unrefs the child if `close` still does not arrive;
  - the new executor stops after scheduling SIGKILL and has no force-bounded failure path;
  - sibling `NodeGitBlobReader` already implements the required bounded lifecycle, including `kill()` result diagnostics and post-SIGKILL forced failure;
  - the new executor test covers a cooperative ordinary timeout only, so the missing termination edge cases remain untested.
- Required action: align metadata/diff execution with the rev5 lifecycle (preferably by sharing a common termination helper with the blob reader): record SIGTERM/SIGKILL send outcomes, keep collecting diagnostics after timeout, convert post-timeout process errors into the timeout failure record, and force a bounded `GitCommandFailedError` after the final grace period. Add tests for SIGTERM-ignoring processes and the no-close/kill-failure branches through an injectable process boundary where necessary.

### R65-003 — MEDIUM — Error de-duplication suppresses required terminal lifecycle events for nested operations

- Origin: `introduced_by_change`
- Location: `src/application/operation-feedback/operation-feedback.ts` (`reportedErrors`, `recordFailure`).
- Description: one process-wide `WeakSet<object>` suppresses every later failure log for the same Error object. If an inner `OperationFeedback.run()` logs the error and rethrows it to an outer `run()`, the outer operation emits `START` but its terminal `ERROR` is suppressed. Reusing the same Error object in a later independent operation is also suppressed for the lifetime of the feedback instance.
- Impact: the Output lifecycle can become structurally incomplete (`START` without `OK`/`ERROR`) exactly in nested operation paths. This conflicts with rev5's per-operation lifecycle contract and makes duration/status diagnosis ambiguous.
- Evidence:
  - every `run()` emits `started` before executing the operation;
  - catch calls `recordFailure()`, but `recordFailure()` returns immediately when the Error is already in `reportedErrors`;
  - the test suite covers nested success and `run()` followed by `reportFailure()` duplication, but does not cover nested failure or reuse across separate runs.
- Required action: scope de-duplication to the intended duplicate boundary (operation wrapper → UI/fail-closed reporter) instead of globally suppressing terminal events. Each `run()` must emit its own terminal failure. Add nested-failure and same-Error-across-separate-runs tests while retaining the UI-boundary duplicate suppression requirement.
