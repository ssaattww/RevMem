## 前回R2指摘の確認

### 1. copy元の確認状態まで解除する

- **解消済み**
- copy経路はsourceを変更せず、destinationだけを`newFiles`から新規未確認stateとして生成する
- 回帰testはsourceの`modifiedReviewed`、`contentHash`、file-level revisionを含むstate全体の維持を確認している

### 2. 末尾改行1個のEOL差を無視できない

- **解消済み**
- `differsByOneTerminalLineBreak`が追加され、CRLF/LF変換と末尾改行1個の追加・削除を全文証明できる
- 完全文がない場合は変更扱いを維持するため、保守的contractも保持されている
- 回帰testはCRLF→LFと末尾改行追加を確認している。実装は追加・削除で対称である

### 3. 曖昧rename後に旧source stateが残る

- **解消済み**
- sourceが複数rename destinationへ対応する場合、旧source file IDを`unresolvedRenameSourceIds`へ入れ、post-transition snapshotから除去する
- destinationは別file IDの新規未確認stateとして生成される

### 4. destination metadata不足でもincomplete snapshotを返す

- **解消済み**
- addition、copy、曖昧renameのdestination metadata不足は`RangeError`となり、結果を返さない
- input snapshotはclone後のローカルstateだけを変更するため、例外時もinput mutationはない
- `missing-new-file-metadata`を通常のunresolved reasonから除去したcontractも整合している

対応要求:

2. T204差分と`package.json`のtest wiringが保持されていることを確認する
3. 統合後HEAD SHAに紐づくfocused testと全CIを成功させる

### [Medium / conservative validation] 重複destinationを持つtransition graphを拒否せず上書きする

`newDestinations`はpathをkeyとする`Map`で、`addDestination`は既存pathの有無を確認せず`set`する。したがって、同じdestination pathを持つ2つのcopy、copyとaddition、または複数additionを含む不正diffでは、後続sectionが同じstateを黙って上書きする。

renameについては`destinationCounts`で一意性を確認するが、copy経路はそのcountを判定に使用せず、additionはcount対象外である。最終snapshotはpath一意になるため`validateStateSnapshot`もこの不正なtransition graphを検出できない。

通常のGit出力では同じnew pathが複数fileとして現れないが、この公開APIはcomplete diff文字列を入力として受け、T203から継続してmalformed inputを推測せず拒否する方針である。重複destinationを正常化して1fileへ畳み込むより、graph構築時に明示的に拒否するべきである。

推奨対応:

- 全`add`、`copy`、`rename`のnew pathを含むdestination countを構築し、同じnew pathが複数sectionに現れた場合は`SyntaxError`または`RangeError`で拒否する
- 2つのcopyが同一destinationを指すfixtureと、copy+additionが同一destinationを指すfixtureを追加する

## 確認済み事項

- source file IDはpre-transition snapshotから解決され、rename chainとswapはsection順に依存しない
- delete+renameによるdestination path再利用は、delete適用後にrenameを反映して正しく成立する
- 100% rename-onlyではstable IDとhashを維持する
- 内容変更renameでは旧hashを除去し、提供された新hashだけを保持する
- mapped intervalはnew line count境界内であることを検証する
- state key/fileId、current path一意性、line count、modified intervalを検証する
- malformed quoted copy path、duplicate metadata、status conflictを拒否する
- copy sourceは維持し、copy destinationだけが新規未確認になる
- split・merge相当をdelete/addまたは曖昧mappingとして表現した場合、destinationはstable IDを継承しない
- 公開type、property、functionのJSDocとbarrel exportは揃っている
- complete diffのparseは1回で、fileごとの完全再parse構造はない
